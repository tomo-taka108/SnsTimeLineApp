# 機能一覧

本書は、本アプリで実装する機能をすべて列挙し、識別子・優先度・関連画面・関連APIを対応付けた**ハブドキュメント**である。
「この機能を変更したら、どの画面とどのAPIに影響するか」を逆引きするために使う。

---

## 1. 機能IDの採番規則

**形式: `F-<カテゴリ2文字>-<連番2桁>`**

| コード | カテゴリ | 説明 |
|---|---|---|
| `AU` | 認証 (Authentication) | 登録・ログイン・ログアウト・パスワード |
| `US` | ユーザー / プロフィール | プロフィールの表示・編集・検索 |
| `PO` | 投稿 (Post) | 投稿の作成・表示・編集・削除 |
| `CM` | コメント (Comment) | コメントの投稿・表示・編集・削除 |
| `LK` | いいね (Like) | いいね・解除・カウント表示 |
| `FL` | フォロー (Follow) | フォロー・解除・一覧 |
| `TL` | タイムライン | 全体TL・フォロー中TL・追加読み込み |
| `IM` | 画像 (Image) | アップロード・配信・バリデーション |
| `CO` | 共通 / 横断 | エラー表示・認証エラー時の遷移 |

**運用ルール:**

- **一度振った機能IDは変更しない。** 機能を削除した場合も番号を再利用せず、「廃止」として残す。
- 新しい機能を追加する場合は、そのカテゴリの**末尾に連番を追加**する。途中に挿入したり枝番（`F-PO-03a`）を使ったりしない。
- 機能IDは [03_screen_design.md](03_screen_design.md)、[04_data_model.md](04_data_model.md)、[05_api_design.md](05_api_design.md) から参照される**一次キー**である。

## 2. 機能の粒度基準

**「ユーザーが1回の操作で達成する1つの目的」= 1機能**とする。

| 判定 | 例 | 理由 |
|---|---|---|
| ✕ 粗すぎる | 「投稿機能」 | 作成・編集・削除で影響範囲もAPIも異なる |
| ✕ 細かすぎる | 「投稿ボタンを押すとローディングが出る」 | UIの挙動であり機能ではない。画面設計に書く |
| ○ 適切 | 「テキストを投稿する」「自分の投稿を削除する」 | ユーザーの目的が1つ、対応APIが1〜2本 |

**目安: 1機能 ≒ 1〜2 APIエンドポイント。**

---

## 3. 優先度の定義

| 優先度 | 定義 | 判断基準 |
|---|---|---|
| **MVP** | これが無いと「SNSとして動く」と言えないもの | [01_requirements.md](01_requirements.md) 6章の「MVPの完成条件」の一周が成立する最小集合 |
| **Phase2** | 一周は成立するが、実運用や体験の質のために欲しいもの | 編集機能、一覧系の派生画面、検索、プロフィール画像 |
| **Phase3** | 学習ゴールを超えるもの。今回は実装しない | 通知、DM、ハッシュタグ、全文検索、ブロック、退会 |

### 優先度の切り分け方針: 「削除はMVP、編集はPhase2」

削除は**誤投稿のリカバリ手段**として必須だが、編集は無くても運用できる（消して投稿し直せる）。
ただし**DBスキーマとAPI設計には最初から編集を織り込む**（`updated_at` / `edited_at` カラム、`PATCH` エンドポイント）。Phase2では実装を足すだけで済むようにする。

### 4.1 認証 (`F-AU-`)

| 機能ID | 機能名 | 概要 | 優先度 | 関連画面 | API # |
|---|---|---|---|---|---|
| F-AU-01 | 新規登録 | メールアドレス・パスワード・ユーザー名・表示名を入力してアカウントを作成する。登録成功時はそのままログイン状態にする | MVP | SC-02 | 1 |
| F-AU-02 | ログイン | メールアドレスとパスワードで認証し、JWTを取得する | MVP | SC-01 | 2 |
| F-AU-03 | ログアウト | `POST /auth/logout` でリフレッシュトークンを失効させ、クライアント側の両トークンを破棄してログイン画面へ遷移する | MVP | 全画面（ヘッダー） | 28 |
| F-AU-04 | ログイン状態の維持 | JWTをブラウザに保持し、リロード後も認証状態を復元する。全APIリクエストに自動付与する | MVP | 全画面 | 3 |
| F-AU-05 | パスワード変更 | 現在のパスワードを検証したうえで新しいパスワードに更新する | Phase2 | SC-11 | 4 |
| F-AU-06 | トークン再発行 | アクセストークンの期限切れ時に、リフレッシュトークンで新しいトークンを取得する。ユーザーには見えない裏の処理 | MVP | 全画面 | 27 |

> **F-AU-03 の補足（更新）**: 当初は「サーバー通信は行わない」設計だったが、リフレッシュトークンの導入（[09_decision_log.md](09_decision_log.md) D-29）により**サーバーに失効を通知する**方式へ変更した。ただし**発行済みのアクセストークンは失効できない**（最大15分間有効なまま）。これはステートレスJWTの本質的な性質であり、有効期限を15分と短くしてこの窓を狭めている。

### 4.3 投稿 (`F-PO-`)

| 機能ID | 機能名 | 概要 | 優先度 | 関連画面 | API # |
|---|---|---|---|---|---|
| F-PO-01 | 投稿作成（テキスト） | 最大280文字の本文を投稿する。投稿後はタイムライン先頭に反映する | MVP | SC-03, MD-01 | 6 |
| F-PO-02 | 投稿作成（画像付き） | 画像を添付して投稿する。MVPでは1枚まで | MVP | SC-03, MD-01 | 6, 25 |
| F-PO-03 | 投稿詳細表示 | 単一の投稿と、それに付いたコメント一覧を表示する | MVP | SC-04 | 7, 10 |
| F-PO-04 | 投稿編集 | 自分の投稿の本文を編集する。編集後は「編集済み」を表示する。**画像の差し替えは対象外** | Phase2 | SC-04, MD-02 | 8 |

### 4.7 タイムライン (`F-TL-`)

| 機能ID | 機能名 | 概要 | 優先度 | 関連画面 | API # |
|---|---|---|---|---|---|
| F-TL-01 | 全体タイムライン表示 | 全ユーザーの投稿を新着順に表示する。タブ名「すべて」 | MVP | SC-03 | 5 |
| F-TL-02 | フォロー中タイムライン表示 | 自分＋フォロー中ユーザーの投稿のみを新着順に表示する。タブ名「フォロー中」 | MVP | SC-03 | 5 |
| F-TL-03 | タイムラインの追加読み込み | 画面下端に到達したら次の20件をカーソルページネーションで読み込む（無限スクロール） | MVP | SC-03, SC-04, SC-05 | 5, 10, 18 |

### 4.8 画像 (`F-IM-`)

| 機能ID | 機能名 | 概要 | 優先度 | 関連画面 | API # |
|---|---|---|---|---|---|
| F-IM-01 | 画像アップロード | 画像ファイルをサーバーに送信し、保存して `fileId` を受け取る。投稿作成とは**独立したAPI** | MVP | MD-01, SC-06 | 25 |

> **F-IM-01 を投稿作成から分離する理由**: 投稿APIをJSONのまま保てる、アップロード進捗を先に表示できる、失敗時のリトライが独立する。詳細は [05_api_design.md](05_api_design.md)。
