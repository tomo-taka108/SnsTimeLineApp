# 設計判断ログ

要件定義フェーズで下した判断と、その理由を記録する。
**「なぜこうなっているのか」を後から思い出すためのドキュメント**であり、実装中に方針がぶれたときの拠り所となる。

## 記録のフォーマット

| 項目 | 内容 |
|---|---|
| ID | `D-nn` |
| 日付 | 判断した日 |
| 論点 | 何を決めようとしたか |
| 選択肢 | 検討した案 |
| 決定 | 採用した案 |
| 理由 | なぜそれを選んだか |
| 影響範囲 | どのドキュメント・実装に影響するか |
| 状態 | 決定済み / 保留 / 撤回 |

**判断を変更する場合は、既存のエントリを書き換えず、新しいIDで追記して古い方を「撤回」にする。** 判断の履歴自体が学習の記録になる。

## D-01: いいね数・コメント数のカウント方式

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-17 |
| **論点** | いいね数・コメント数をどう保持・取得するか |
| **選択肢** | A. 都度 `COUNT(*)` / **B. 非正規化カウンタカラム** / C. 集計テーブル・キャッシュ |
| **決定** | **B. 非正規化カウンタ**（`posts.like_count` / `posts.comment_count`） |
| **状態** | 決定済み |

**理由**

1. **学習価値が最も高い。** 「非正規化を導入すると、代わりにトランザクション整合性の責任が発生する」というRDB設計の核心を実地で学べる。A案では得られない。
2. タイムライン20件×2種のカウントで相関サブクエリが走る、**非正規化が正当化される典型パターン**である。
3. C案は学習段階では過剰。

**推奨する学習ステップ**: 最初にA案で実装し、`EXPLAIN ANALYZE` で遅さを確認してからB案にリファクタリングすると、非正規化の必要性を体感できる。

**受け入れたトレードオフ**: カウンタがズレるリスク。以下で担保する。
- 同一トランザクションで更新する
- SQL側で相対更新する（`SET like_count = like_count + 1`）
- 再集計SQLを用意する

**影響範囲**: [04_data_model.md](04_data_model.md) 2.2, 3.1 / [05_api_design.md](05_api_design.md) #11, #13, #14, #15 / [06_non_functional.md](06_non_functional.md) 5.3

## D-02: 論理削除の適用範囲

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-17 |
| **論点** | どのテーブルを論理削除にするか |
| **選択肢** | A. 全テーブルを論理削除 / **B. `posts`/`comments`/`users` のみ論理削除、`likes`/`follows` は物理削除** |
| **決定** | **B** |
| **状態** | 決定済み |

**理由**

- `likes` を論理削除にすると `UNIQUE (post_id, user_id)` が機能しなくなる。「いいね→解除→再いいね」で削除済み行が残り、2回目のINSERTが制約違反になる。
- 部分ユニークインデックス（`UNIQUE ... WHERE deleted_at IS NULL`）で回避できるが、学習段階では複雑さに見合わない。
- そもそも**いいね・フォローは「取り消した履歴」を残す価値がない**。

**付随して決めたこと**

| 項目 | 決定 |
|---|---|
| カスケード | 投稿を論理削除しても、コメント・いいね・画像実体は**追い削除しない**（到達不能になるため不要） |
| カウンタの非対称ルール | **投稿**の論理削除では `comment_count` を触らない。**コメント**単体の論理削除では -1 する |
| 論理削除済みへのGET | `404 Not Found`。`410 Gone` は使わない（存在の有無を漏らさないため） |
| 実現方法 | Hibernateの `@SQLRestriction("deleted_at is null")` |

**影響範囲**: [04_data_model.md](04_data_model.md) 3.2 / [05_api_design.md](05_api_design.md) #7, #9, #13 / [06_non_functional.md](06_non_functional.md) 5.3

## D-03: コメントのネスト構造

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-17 |
| **論点** | コメントに返信（ネスト）を許すか |
| **選択肢** | A. 無限ツリー（Reddit型） / B. 1階層の返信（Slackスレッド型） / **C. ネストなし（フラット）** |
| **決定** | **C. フラット。`parent_comment_id` を持たない** |
| **状態** | 決定済み |

**理由**

1. ネストを許すと**再帰クエリ・ツリー描画・深さ制限・親削除時の子の扱い**が一気に増える。要件定義フェーズで避けるべき複雑さ。
2. **ツリー構造ではページネーション自体が難問**になる。フラットなら `post_id` に対する単純なカーソルページネーションで済む。
3. 「投稿詳細にコメントが時系列で並ぶ」形で学習ゴールは十分満たせる。

**将来の拡張余地**: Phase3で必要になれば `parent_comment_id BIGINT NULL REFERENCES comments(id)` を追加する。ただし**2階層以上は許さない**（返信への返信は同じ親にぶら下げる = Slackスレッド型）。これで再帰クエリを回避できる。

**代替手段**: 「誰への返信か」は本文中の `@ユーザー名` メンションで表現できる。

**影響範囲**: [04_data_model.md](04_data_model.md) 2.3, 3.3 / [01_requirements.md](01_requirements.md) 3.2

## D-05: 画像ストレージの抽象化方法

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-17 |
| **論点** | 将来S3に差し替えられるようにするには、DBに何を保存すべきか |
| **選択肢** | A. 絶対URLを保存 / B. 物理パスを保存 / **C. `storage_type` + `storage_key` を保存し、URLはアプリ層で生成** |
| **決定** | **C。`stored_files` テーブルを独立させる** |
| **状態** | 決定済み |

**理由**

| 保存内容 | ローカル→S3移行時 |
|---|---|
| A. 絶対URL | 全レコードの書き換えが必要。ドメイン変更でも壊れる |
| B. 物理パス | OS依存。サーバー移設で全滅 |
| **C** | **`storage_type` を更新し、設定値を変えるだけ。`storage_key` は流用できる** |

**付随して決めたこと**

| 項目 | 決定 |
|---|---|
| URL生成の責務 | アプリ層の `FileStorageService#generateUrl`。**DBはURLを知らない** |
| `storage_key` の形式 | `2026/08/17/{UUID}.jpg`。日付ディレクトリで分散、UUIDで衝突回避 |
| 元のファイル名 | `original_filename` に保存するが、**パスには使わない**（パストラバーサル対策） |
| `stored_files` の共用 | 投稿画像とプロフィール画像で同じテーブル・同じアップロードAPIを使う |
| `width` / `height` の保持 | フロントがレイアウトシフトを防ぐために必要 |

**影響範囲**: [04_data_model.md](04_data_model.md) 2.7, 3.5 / [07_architecture.md](07_architecture.md) 3章 / [05_api_design.md](05_api_design.md) #25, #26

## D-06: ページネーション方式

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-17 |
| **論点** | 一覧取得のページネーション方式 |
| **選択肢** | A. オフセット（`LIMIT`/`OFFSET`） / **B. カーソル（Keyset Pagination）** |
| **決定** | **B。ただしユーザー検索のみA** |
| **状態** | 決定済み |

**理由**

1. **オフセットは重複・欠落が必ず発生する。** `LIMIT 20 OFFSET 20` を投げる間に新しい投稿が1件入ると全体が1つずれ、2ページ目の先頭が1ページ目の末尾と重複する。無限スクロールUIでは致命的。
2. 深いページ（`OFFSET 10000`）でスキャンコストが線形に増える。
3. **「なぜSNSは軒並みカーソル方式なのか」を体感できる**という学習価値。

**カーソルの仕様**

| 項目 | 決定 |
|---|---|
| 中身 | `(created_at, id)` をJSON化してBase64エンコードした**不透明な文字列** |
| タイブレーカー | **`id` を必ず含める。** 同一 `created_at` の投稿で取りこぼすため |
| クライアントの扱い | 中身を解釈せず、次のリクエストにそのまま渡す |
| `hasNext` の判定 | `LIMIT 21` で1件多く取得し、21件返ったら `true` |

**例外（オフセットを使う箇所）**: ユーザー検索（#20）。結果が安定しており、ページ番号UIが自然なため。
**ページネーション方式は機能ごとに選ぶもの**であり、統一する必要はない。この使い分け自体が学習ポイント。

**影響範囲**: [05_api_design.md](05_api_design.md) 2章 / [04_data_model.md](04_data_model.md) 4.2, 5.1, 5.2 / [03_screen_design.md](03_screen_design.md) SC-03

## D-07: JWTの保管場所

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-17 |
| **論点** | クライアント側でJWTをどこに保持するか |
| **選択肢** | **A. `localStorage`** / B. httpOnly Cookie |
| **決定** | **A. `localStorage`** |
| **状態** | 決定済み |

**理由**

| 保管場所 | メリット | リスク |
|---|---|---|
| **localStorage** | 実装が単純。別オリジンでも `Authorization` ヘッダーで送れる。**CSRF対策が不要** | XSSでトークンを盗まれる |
| httpOnly Cookie | XSSで読み取れない | **CSRF対策が必須**。別オリジンだと `SameSite` の設定が複雑 |

学習用途かつ別オリジン構成のため、実装の単純さを優先した。

**受け入れたトレードオフとその前提**

XSSリスクを受け入れる代わりに、**XSS自体を起こさない実装を徹底する**ことが前提。

- `dangerouslySetInnerHTML` を使わない
- ユーザー入力をHTMLとして解釈しない
- 本文中のURLを自動リンク化する場合、`javascript:` スキームを弾く

> **実務では httpOnly Cookie + CSRFトークンが推奨される。** 本アプリの選択は学習用途の割り切りであり、この判断の意味を理解しておくことが重要。

**付随する決定**: `allowCredentials: false` にできる（Cookieを使わないため）。

**影響範囲**: [06_non_functional.md](06_non_functional.md) 3.3 / [05_api_design.md](05_api_design.md) 7章 / [07_architecture.md](07_architecture.md) 4.1

## D-08: いいね・フォローAPIのHTTPメソッド

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-17 |
| **論点** | いいね・フォローの追加/解除をどのメソッドで表現するか |
| **選択肢** | A. `POST /like` + `POST /unlike` / **B. `PUT /like` + `DELETE /like`** |
| **決定** | **B** |
| **状態** | 決定済み |

**理由**

1. 操作対象のリソースは「**その投稿に対する自分のいいね**」であり、`PUT` は「その状態にする」という**冪等な操作**として自然に対応する。
2. `PUT` は「何回実行しても同じ結果」がHTTPの規約。**二重クリックで409を返す必要がない。**
3. 楽観的UI更新で連打されてもサーバー側でエラーにならない。

**実装方針**: 既にいいね済みの状態で `PUT` が来たら、UNIQUE制約違反を捕捉して**カウンタを更新せずに200を返す**。

**付随する決定**: レスポンスは `204` ではなく **`200 OK` + 更新後のカウント**。クライアントが再取得せずにUIを更新できるため。同じ理由でコメント削除（#13）も200を返す。

**影響範囲**: [05_api_design.md](05_api_design.md) 3.1, #13, #14, #15, #21, #22 / [04_data_model.md](04_data_model.md) 3.6

## D-09: 画像アップロードと投稿作成の分離

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-17 |
| **論点** | 画像付き投稿をどう作るか |
| **選択肢** | A. `POST /posts` に multipart で本文と画像を同時送信 / **B. `POST /files` で先にアップロードし、`fileId` を `POST /posts` に渡す** |
| **決定** | **B** |
| **状態** | 決定済み |

**理由**

| メリット | 内容 |
|---|---|
| 投稿APIをJSONに保てる | multipartとJSONが混在せず設計が単純 |
| 体感速度が上がる | ユーザーが本文を入力している間に、裏でアップロードを完了できる |
| リトライが独立する | アップロードだけ失敗した場合、本文を再入力させずに済む |
| 基盤を再利用できる | プロフィール画像（F-US-04）も同じ `POST /files` を使える |

**受け入れたトレードオフ**: 投稿せずに離脱すると**孤児ファイル**が残る（R-03）。MVPでは許容し、Phase3で定期クリーンアップを検討する。検出クエリは [04_data_model.md](04_data_model.md) 3.5に記載済み。

**付随して決めたこと**: `POST /posts` で `imageFileIds` を受け取る際、**そのファイルが自分のアップロードしたものか検証する**（他人の画像を勝手に添付できないようにする）。見落としやすいポイント。

**影響範囲**: [05_api_design.md](05_api_design.md) 3.1, #6, #25 / [03_screen_design.md](03_screen_design.md) MD-01

## D-13: IDをJSONで数値のまま返すか

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-17 |
| **論点** | `BIGINT` のIDをAPIレスポンスでどう表現するか |
| **選択肢** | **A. 数値のまま** / B. 文字列に変換 |
| **決定** | **A。ただし制約を認識しておく** |
| **状態** | 決定済み |

**理由**: `BIGINT` の最大値はJavaScriptの安全整数（2^53-1）を超えうるため、実務では文字列で返すことが多い。本アプリは学習用途でIDが小さく収まるため数値のままとする。

**認識しておくべき制約**: 実務で大規模なIDを扱う場合は文字列化が必要になる。この問題の存在を知っておくこと自体が学習ポイント。

## D-19: ユーザー検索のマッチング方式

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-18 |
| **論点** | ユーザーをどうやって検索するか（F-US-05 / API #20） |
| **選択肢** | A. `ILIKE '%q%'` のみ（インデックスなし） / B. 最初から pg_trgm 中間一致 / **C. 前方一致 → pg_trgm の段階式** |
| **決定** | **C。第1段階で前方一致、第2段階で pg_trgm によるあいまい一致に拡張する** |
| **状態** | 決定済み |

**検索対象**: `username` と `display_name` の2つ。**`bio` は検索意図と合わないため除外、`email` はアカウント列挙を招くため絶対に含めない。**

**理由**

1. **「B-treeインデックスは前方一致までしか効かない」という原則を体感できる。** `lower(username) LIKE 'tar%'` は `Index Scan` になるが `'%aro%'` は `Seq Scan` になる。段階を分けることで `EXPLAIN ANALYZE` の比較ができる。
2. A案は実装が最も簡単だが全件走査になる。B案は一発で高機能な代わりに、上記の学習ポイントを飛ばしてしまう。
3. 想定ユーザー数100人（[06_non_functional.md](06_non_functional.md) 1.1）なら、第1段階の前方一致だけでも実用上は十分に機能する。**第2段階は「必要になったから足す」形にできる。**

**実装上の要点**

| # | 要点 |
|---|---|
| 1 | `ILIKE` ではなく `lower(col) LIKE` を使う。**`ILIKE` は式インデックス `lower(col)` を使ってくれない** |
| 2 | pg_trgm では `WHERE` に `%` 演算子を使い、`similarity()` は `ORDER BY` にだけ置く。**`WHERE similarity(...) > 0.3` と書くとGINインデックスが効かない** |
| 3 | `q` の `%` と `_` を必ずエスケープする。**`q=%` で全ユーザーが列挙される** |
| 4 | `ORDER BY` に `id` をタイブレーカーとして必ず含める。オフセット方式でも順序不定は取りこぼしを生む |
| 5 | 検索結果の `isFollowing` は一括取得する。`isLikedByMe` と同じN+1パターン |

**受け入れたトレードオフ**: 第1段階では「田中たろう」を「たろう」で検索してもヒットしない。第2段階の実装までは、ユーザーに前方一致であることが伝わるUIにするか、早めに第2段階へ進む。

**影響範囲**: [04_data_model.md](04_data_model.md) 4章, 6章 / [05_api_design.md](05_api_design.md) #20, `UserListItem` / [03_screen_design.md](03_screen_design.md) SC-07 / [06_non_functional.md](06_non_functional.md) 3.6

## D-25 O/RマッパーにMyBatisを採用する

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-23 |
| **論点** | DBアクセスに JPA/Hibernate と MyBatis のどちらを使うか |
| **選択肢** | A. JPA (Hibernate) / **B. MyBatis** |
| **決定** | **B。MyBatis（`mybatis-spring-boot-starter` 4.1.0）を採用する** |
| **状態** | 決定済み |

**理由**

1. 発行されるSQLがコードと1対1で対応するため、[06_non_functional.md](06_non_functional.md) 1.3 が求める「タイムライン取得のSQL発行回数は3回以内」「N+1を作らない」を**目で確認しながら実装できる**。学習目的に適う。
2. 非正規化カウンタのSQL側相対更新（D-01）のような「SQLをそのまま書きたい」要件と相性がよい。

**トレードオフ（受け入れるリスク）**

MyBatis には Hibernate の `@SQLRestriction` に相当する**論理削除の自動除外機能がない**。各SQLに `deleted_at IS NULL` を手で書くことになり、D-02 が警戒していた「1箇所の書き忘れで削除済みレコードが漏れる」リスクは**JPAより高くなる**。対策として以下3つの歯止めを置く。

| # | 歯止め |
|---|---|
| 1 | SQLはMapper XMLに集約し、`<sql id="activeOnly">deleted_at IS NULL</sql>` を `<include>` で使い回す（条件を1箇所で管理する） |
| 2 | 論理削除を意図的に無視するメソッドは名前に `IncludingDeleted` を付け、逸脱が名前で分かるようにする |
| 3 | レビュー時に `FROM users` を含むSQLに除外条件があるかを機械的に確認する |

**意図的な例外**: 重複チェック（`existsByEmailIncludingDeleted` / `existsByUsernameIncludingDeleted`）は `deleted_at IS NULL` を**付けない**。一意制約が `deleted_at` を絡めない設計＝退会したメール・ユーザー名は再利用させない方針のため、退会済みユーザーも重複として扱うのが正しい（[04_data_model.md](04_data_model.md) 2.1）。

**この決定に伴う撤回**

- **D-02 の「実現方法: Hibernateの `@SQLRestriction`」を撤回する。** 論理削除を採用する方針（`posts` / `comments` / `users` のみ論理削除、`likes` / `follows` は物理削除）自体は**変更しない**。
- **D-18（論理削除の実現方法）を決着させる。** MyBatis には自動除外機構が存在しないため、選択肢のうち「明示的なリポジトリメソッド」側に確定する。

**影響範囲**: [04_data_model.md](04_data_model.md) 3.2 / [06_non_functional.md](06_non_functional.md) 3.7 / [07_architecture.md](07_architecture.md) 2.2

## D-26 JWTライブラリに jjwt を採用する（GSON版）

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-23 |
| **論点** | JWTの生成・検証に使うライブラリ |
| **選択肢** | **A. jjwt** / B. nimbus-jose-jwt / C. Spring Security OAuth2 Resource Server |
| **決定** | **A。jjwt 0.12.7。ただし `jjwt-jackson` ではなく `jjwt-gson` を使う** |
| **状態** | 決定済み |

**理由**

1. [06_non_functional.md](06_non_functional.md) 3.2 が要求する「**`alg: none` を受け入れない**」が、jjwt では**設定ではなく既定の動作**として満たされる。`parseSignedClaims()` はJWSを必須とし、未署名トークンを受け入れるには明示的に `.unsecured()` を呼ぶ必要がある。「安全側が既定」であることが学習用途として重要。
2. 秘密鍵が256bit未満なら `WeakKeyException` を投げるため、「32バイト以上」の要求も起動時に強制できる。
3. B案は `JWSVerifier` を自前で組み `alg` を手動検査する必要があり、間違える余地が大きい。C案は対称鍵のトークンにリソースサーバー一式を持ち込むことになり、[07_architecture.md](07_architecture.md) 2.2 が想定する自前の `JwtTokenProvider` 構成と矛盾する。

**GSON版を選ぶ理由**: jjwt は内部シリアライザが Jackson 2 依存で、**Jackson 3 に未対応**（[jwtk/jjwt#1029](https://github.com/jwtk/jjwt/issues/1029)）。Spring Boot 4 の既定は Jackson 3（`tools.jackson`）のため、`jjwt-jackson` を使うと Jackson 2 が混在する。JWTのペイロードは `sub` / `iat` / `exp` のみで GSON に不足はない。

**検証済み**: `alg: none` で細工したトークンを `GET /auth/me` に送り、401 `UNAUTHENTICATED` が返ることを確認した。

## D-27 パスワードは前後の空白をトリムしない

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-23 |
| **論点** | [05_api_design.md](05_api_design.md) 8章「文字列は前後の空白をトリムしてから検証する」をパスワードにも適用するか |
| **選択肢** | A. 全文字列を一律トリム / **B. パスワードだけ除外する** |
| **決定** | **B。`email` / `username` / `displayName` はトリムし、`password` はトリムしない** |
| **状態** | 決定済み |

**理由**

前後の空白も**正当なパスワード文字**である。黙って除去すると、ユーザーが他所（パスワードマネージャ等）で正しく設定したパスワードでログインできなくなる。8章の規約は表示用の文字列を想定したものであり、認証情報には適用しない。

**実装**: トリムは Jackson のデシリアライズ時に行う（`TrimDeserializer`）。「ボディのデシリアライズ→`@Valid`」の順で処理されるため、検証した文字列と保存する文字列が一致する。`WebDataBinder` + `StringTrimmerEditor` はJSONボディに効かないため使わない。

## D-29 アクセストークン＋リフレッシュトークン方式を採用する

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-23 |
| **論点** | JWTの有効期限とリフレッシュの扱い |
| **選択肢** | A. 単一トークン（24時間、リフレッシュなし） / **B. アクセストークン（15分）＋リフレッシュトークン（14日）** |
| **決定** | **B。2種類のトークンに役割を分ける** |
| **状態** | 決定済み |

**この決定は [D-07](#d-07-jwtの保管場所) を撤回しない。** 保管場所は引き続き `localStorage`（両方のトークンを置く）。

### 撤回する判断

当初の設計（[05_api_design.md](05_api_design.md) 1.2、[01_requirements.md](01_requirements.md) 3.2）は
「**リフレッシュは行わない。期限切れは再ログイン**」「トークンの失効管理は行わない」としていた。**この2点を撤回する。**

### 理由

単一トークン方式は、**有効期限を長くしても短くしても片方が悪化する**という構造的な問題を抱えていた。

| 有効期限 | セキュリティ | 使い勝手 |
|---|---|---|
| 24時間（旧設計） | **漏洩したトークンが24時間使い放題**。JWTは失効させられないため止める手段がない | 良い |
| 15分（単一のみ） | 被害時間は短い | **15分ごとに再ログイン**。実用に耐えない |

2種類に分けると、この二律背反が解ける。

| | アクセストークン | リフレッシュトークン |
|---|---|---|
| 形式 | JWT（HS256、ステートレス） | **不透明トークン**（ランダム256bit、DB保存） |
| 有効期限 | **15分** | **14日** |
| 用途 | 毎回のAPI呼び出し | アクセストークンの再発行のみ |
| 失効 | **できない**（ステートレスの代償） | **できる**（DBに状態がある） |
| 送信先 | すべての保護されたAPI | `POST /auth/refresh` だけ |

**要点は「頻繁に飛ぶものほど短命に、失効できるものほど長命に」**。アクセストークンは毎リクエスト飛ぶので漏洩機会が多いが15分で無効化される。リフレッシュトークンは長命だが、送信頻度が低く、かつDBで失効できる。

### 付随して決めたこと

| # | 決定 | 理由 |
|---|---|---|
| 1 | リフレッシュトークンは**JWTにしない**（不透明なランダム文字列） | JWTにすると「失効できない」問題を長命側にも持ち込むことになり、分けた意味がなくなる |
| 2 | DBには**SHA-256ハッシュで保存**する | DB漏洩時にそのまま使われないため。**BCryptは使わない** — ランダム256bitで総当たりが成立せず、低速ハッシュの必要がない（パスワードとの違い） |
| 3 | **1回使ったら使い捨て**（ローテーション） | 使用済みトークンの再提示を盗用のサインとして検知できるようにするため |
| 4 | 使用済みトークンが再提示されたら**ファミリー全体を失効**させる | 攻撃者と正規ユーザーのどちらが提示したか判別できないため、両方に再ログインを強制する（安全側に倒す） |
| 5 | `POST /auth/refresh` は**認証不要**（permitAll） | 期限切れのアクセストークンしか持たない状態で呼ぶAPIのため。ボディのリフレッシュトークン自体が認証情報になる |
| 6 | `POST /auth/logout` は**認証必要** | 「誰のトークンを失効させるか」をアクセストークンから決める。他人のリフレッシュトークンを送りつけて失効させる妨害を防げる |
| 7 | 失敗理由を区別せず**すべて `INVALID_REFRESH_TOKEN`（401）** | 「存在するが失効済み」といった情報を攻撃者に与えないため |

> **ファミリーとは**: ログイン1回分のトークンの連鎖。ローテーションで新しいトークンを作っても同じ `family_id` を引き継ぐため、盗用検知時に「そのログインに由来するトークン」だけをまとめて失効できる。**他の端末のログインは巻き込まない。**

### 受け入れるトレードオフ

| # | 内容 |
|---|---|
| 1 | **ログアウトしても、発行済みアクセストークンは最大15分間有効なまま。** ステートレスJWTの本質的な性質であり、これを消すにはリクエストごとにDBを引く（＝ステートレスをやめる）しかない。**有効期限を15分と短くしているのは、この窓を狭めるため** |
| 2 | **DBアクセスが増える**（リフレッシュ時のSELECT + UPDATE + INSERT）。ただし15分に1回程度であり、毎リクエストではない |
| 3 | **期限切れ行が溜まる。** MVPでは掃除しない。定期削除は [D-16](#未決事項保留) と同じくPhase3で検討する |
| 4 | クライアント側の実装が複雑になる（401を受けたら自動リフレッシュして再試行する処理が必要） |

### 実装時に踏んだ罠（重要）

**盗用検知の失効が、直後に投げる401でロールバックされていた。**

`rotate()` は `@Transactional` であり、「ファミリーを失効させる → 401を投げる」という流れになっている。ところが例外（RuntimeException）はトランザクションをロールバックさせるため、**失効そのものが巻き戻る**。ログには「失効させました」と出るのにDBは無傷、という状態だった。

検証で「一括失効したはずのトークンが200を返す」ことに気づいて発覚した。対策として `RefreshTokenRevoker` を別Beanに切り出し、`@Transactional(propagation = REQUIRES_NEW)` で独立したトランザクションにした。

> **同一クラス内のメソッド呼び出しでは `REQUIRES_NEW` が効かない。** Springのトランザクションはプロキシ経由で適用されるため、自己呼び出しはプロキシを通らない。**別のBeanに分ける必要があるのはそのため。**

**影響範囲**: [01_requirements.md](01_requirements.md) 3.2 / [05_api_design.md](05_api_design.md) 1.2・#4・#5 / [06_non_functional.md](06_non_functional.md) 3.2 / [07_architecture.md](07_architecture.md) 4.1・5章 / [04_data_model.md](04_data_model.md)（`refresh_tokens` テーブル追加）

## D-33 カーソルの時刻精度をマイクロ秒に変更する（[D-06](#d-06-ページネーション方式)の一部を撤回）

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-24 |
| **論点** | D-06で定めたカーソルの時刻精度（秒）が、タイムラインのページングで投稿を取りこぼす不具合を引き起こすことが実装時に判明した |
| **選択肢** | A. D-06どおり秒精度のまま実装する / **B. マイクロ秒精度に変更する** |
| **決定** | **B** |
| **状態** | 決定済み（D-06のカーソル精度に関する記述を撤回） |

**問題の詳細**

D-06はカーソルを `{"c":"<ISO8601 UTC 秒精度>","i":<id>}` と定めていたが、**秒に丸めると行値比較 `(created_at, id) < (cursor)` で同一秒内の投稿を取りこぼす。** 丸めた `created_at` は真の値より小さくなるため、同じ秒に投稿された行が「カーソルより古くない」と誤って判定され、次ページから漏れる。

**実装時に25件を一括投稿してページングを検証したところ、実際に発生することを確認した。** 一時テーブルで秒精度のカーソルとマイクロ秒精度のカーソルを比較したところ、秒精度では2ページ目が0件になり、マイクロ秒精度では正しく残り3件が返った。

**対応**

- カーソルの `c` フィールドをマイクロ秒精度（`yyyy-MM-dd'T'HH:mm:ss.SSSSSS'Z'`）に変更する。
- Base64はURLセーフ版を使う（標準Base64の `+` がクエリ文字列で空白に化ける問題への対処。これはD-06の対象外だった追加の修正点）。

## D-34 いいねの冪等性は事前SELECTで確保する（`DuplicateKeyException` 捕捉は不採用）

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-25 |
| **論点** | いいねAPI（#14）の二重登録（`uq_likes_post_user` 違反）をどう冪等に処理するか |
| **選択肢** | A. `GlobalExceptionHandler` の `DataIntegrityViolationException` ハンドラに任せる / B. `LikeService` 内で `DuplicateKeyException` を個別に捕捉する（`AuthService.signup` と同じパターン） / **C. INSERT前に `LikeMapper.exists` で存在確認する** |
| **決定** | **C** |
| **状態** | 決定済み（B案は実装・動作確認の結果、不採用と判明） |

**理由**

既存の `GlobalExceptionHandler.handleDataIntegrity` は認証機能（signup）専用の保険ハンドラで、`EMAIL_ALREADY_EXISTS` 固定でエラーを返す。いいねの二重登録をここに落とすと「いいね済みなのにメール重複エラー」という誤った応答になるため、A案は採らない。

**B案（`AuthService.signup` と同じ `DuplicateKeyException` 捕捉）は、実装して動作確認したところ500エラーになることが判明した。** PostgreSQLは制約違反が起きたトランザクションを「中断状態」にし、Javaで例外を捕捉しても**同一トランザクション内の以降の文をすべて拒否する**。`signup` は違反を検知したらそのまま例外を投げて終了するため問題にならないが、いいねは「重複を無視してカウントを返す」という**その後の処理が続く**冪等API であるため、この違いが致命的だった（`likeMapper.findLikeCount` が `current transaction is aborted` で失敗し500になった）。

`@Transactional(propagation = REQUIRES_NEW)` で挿入だけを別トランザクションに分離する案も検討したが、同一クラス内の自己呼び出しはSpringのプロキシ機構をバイパスし、`REQUIRES_NEW` が効かない（プロキシを経由しないメソッド呼び出しはAOPアドバイスの対象外になる）ため、これも避けた。

**結果、C案（INSERT前に存在確認）を採用する。** TOCTOU（確認直後に他リクエストが挿入する競合）は理論上残るが、UNIQUE制約が最後の砦として機能し、その場合のみ500になる。個人が単一ボタンを連打する程度の同時実行では起きない極めて稀なケースであり、事前確認で実用上十分に防げる。

**影響範囲**: バックエンド実装（`post/LikeMapper.java`, `post/LikeMapper.xml`, `post/LikeService.java`）

| **論点** | 5MB超のアップロードが 500 になり、[06_non_functional.md](06_non_functional.md) 3.5 が要求する 413 を返せない |
| **選択肢** | A. `spring.servlet.multipart.max-file-size` をアプリの上限（5MB）と一致させる / **B. multipart 上限を余裕のある値にし、5MB判定はサービス層で行う。Springの例外はハンドラで413に変換する** |
| **決定** | **B** |
| **状態** | 決定済み |

**理由**

Springのmultipart制限は**Controllerに入る前**に発火するため、`FileService` のサイズ検証には到達しない。Aだけを行うと例外は出るが、それを誰も捕捉しなければ 500 のままで、エラーコード `FILE_TOO_LARGE` も返せない。

Bにより、通常のサイズ超過は設計どおり 413 + `FILE_TOO_LARGE` を返し、`app.upload.max-size-mb` の1箇所で上限を管理できる。multipart側の20MBは「極端に巨大なリクエストをTomcatの段階で切る」最後の防波堤として残す。`GlobalExceptionHandler` にハンドラを追加したのは、それでも到達しうる経路（20MB超）を500にしないため。

**影響範囲**: `common/GlobalExceptionHandler.java` / `application.yml`（`spring.servlet.multipart`）

## D-43 `PATCH /users/me` の存在しない `avatarFileId` は404を返す

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-29 |
| **論点** | [05_api_design.md](05_api_design.md) #19 のエラー欄は403のみ記載しており、404が列挙されていない。#6（投稿への画像添付）は404/403の両方が仕様どおりだが、#19は非対称になっている |
| **選択肢** | A. 設計書の記載どおり403のみ返す（存在しないIDも他人のIDも同じ扱い） / **B. #6と揃えて404→403の順で返す** |
| **決定** | **B** |
| **状態** | 決定済み |

**理由**

認可は「①存在チェック→404、②所有者チェック→403」の順序に統一している（D-14）。この規約は特定のAPIに限定したものではなく全APIに共通する原則であり、#19だけ例外にする理由がない。実装では所有者チェックを`FileService.assertOwnedBy`に集約しており（D-44）、#6と#19が同じメソッドを呼ぶため、自然に同じ順序・同じレスポンスになる。設計書#19の403のみという記載は、単に記載が漏れていたものと判断する。

**影響範囲**: [05_api_design.md](05_api_design.md) #19（エラー欄に404を追記）/ `user/UserService.java`

## D-44 ファイルの所有者チェックは `FileService` に集約する

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-29 |
| **論点** | 投稿への画像添付（#6）とプロフィール画像（#19）の両方で、「指定された`fileId`は自分がアップロードしたものか」という所有者チェックが必要になる。この検証ロジックをどこに置くか |
| **選択肢** | A. `PostService` / `UserService` がそれぞれ `FileMapper` を直接使って検証する / **B. `FileService.assertOwnedBy(meId, fileId)` を公開し、他モジュールはこれだけを呼ぶ** |
| **決定** | **B** |
| **状態** | 決定済み |

**理由**

`LikeService` と `PostService` を分けたのと同じ単一責任の考え方。`stored_files` の存在確認・所有者判定というファイルモジュール固有の知識を、投稿やユーザーのモジュールに漏らさない。Aだと`PostService`と`UserService`それぞれに同じロジックが重複し、将来ファイルの検証条件が変わったとき（例: 削除済みファイルの扱い）に複数箇所を直す必要が出る。

Bにより、D-43の404→403の順序も1箇所に閉じ込められ、呼び出し側は「例外が飛んでこなければ自分のファイル」という単純な前提で書ける。

## D-45 `PostSummary.from()` は画像を引数で渡す（オプショナルにしない）

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-29 |
| **論点** | 画像機能の実装により `PostSummary.from(row, isLikedByMe)` に `images` を追加する必要が生じた。呼び出し箇所は `getTimeline` / `getUserPosts` / `getById` / `create` / `update` の5箇所 |
| **選択肢** | A. `images` にデフォルト値（空リスト）を持たせ、渡さない呼び出しはそのまま動くようにする / **B. 第3引数として必須にする** |
| **決定** | **B** |
| **状態** | 決定済み |

**理由**

Aは実装が楽だが、「画像を一括取得したのに渡し忘れて空配列のまま」という静かなバグを許してしまう。Javaのオーバーロードやデフォルト引数に相当する仕組みは無いため、Aを実現するには別名メソッド（`from(row, isLikedByMe)`と`from(row, isLikedByMe, images)`の2つ）を用意することになり、どちらを呼ぶべきかが呼び出し側の注意力に依存してしまう。

Bなら、5箇所すべてで画像を渡さないとコンパイルが通らないため、実装漏れをコンパイラに検出させられる。実際、`likedPostIdsOf`と同じパターンで`imagesOf`ヘルパーを用意し、5箇所すべてで一貫して呼び出す形にした。

**影響範囲**: `post/dto/PostSummary.java` / `post/PostService.java`

## D-46 画像の拡大表示（ライトボックス）は `Modal` を再利用せず専用コンポーネントにする

## D-47 画像URLのオリジン解決はフロント側で行う

| 項目 | 内容 |
|---|---|
| **日付** | 2026-08-30 |
| **論点** | `avatarUrl` / `PostImageSummary.url` はバックエンドが `/api/v1/files/{id}` という相対パスを返す（設計判断⑤、LOCAL/S3切り替えの独立性のため）。ブラウザ確認で「投稿画像・アバター画像が表示されない」不具合が見つかった。原因はフロント（:5173）とバックエンド（:8080）が別オリジンのため、相対パスをそのまま `<img src>` に渡すとフロント自身へのリクエストになってしまうこと |
| **選択肢** | A. バックエンドが絶対URLを組み立てて返す / **B. フロント側で `VITE_API_BASE_URL` のオリジンを前置して解決する** |
| **決定** | **B** |
| **状態** | 決定済み |

**理由**

バックエンドに絶対URLを組み立てさせると、`app.storage.type` や動作環境（本番ドメイン等）の知識をレスポンス生成のたびに持ち込むことになり、設計判断⑤の「保存先の詳細をURLに持ち込まない」方針と逆行する。フロントは元々 `VITE_API_BASE_URL` で自分がどのオリジンのAPIを呼んでいるかを知っているため、そこからオリジンだけを取り出して相対パスに前置する方が責務が自然に収まる。

`frontend/src/api/files.ts` に `resolveFileUrl(path: string | null): string | null` を追加し、サーバーレスポンスの画像パスを表示する箇所（`Avatar` / `PostImage` / `PostComposer` のプレビュー / `ProfileEditPage`）はすべてここを通す。

**影響範囲**: `api/files.ts`（`resolveFileUrl` 追加）/ `components/Avatar.tsx` / `components/PostImage.tsx` / `components/PostComposer.tsx` / `pages/profile/ProfileEditPage.tsx`
