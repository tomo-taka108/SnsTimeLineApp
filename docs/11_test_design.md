# テスト設計（テストケース表）

本書は、テストコードを書く**前**にテストケースを設計するための文書である。

> **なぜ表を先に作るのか。** 実装を読んでから「危なそうな所」を勘で拾うと、
> ①**境界値が漏れる**、②**実装が仕様を取り違えていた場合にテストも同じ勘違いをする**、
> という2つの問題が起きる。入力を同値クラスに分け、境界を機械的に列挙し、
> **期待値は実装ではなく設計書から引く**ことでこれを防ぐ。

---

## 0. 用語と方針

### 0.1 ブラックボックス / ホワイトボックス

| 技法 | 何を見て作るか | 本書での使い方 |
|---|---|---|
| **ブラックボックス** | 仕様書のみ。中身は見ない | **期待値の列は必ずこちら**。設計書の該当箇所を「根拠」列に書く |
| **ホワイトボックス** | 実装の分岐・経路 | **ケースの取りこぼし確認**に使う。表を作った後に実装と突き合わせ、通っていない経路が無いか確認する |

**両方を使う。** ブラックボックスだけだと実装固有の落とし穴（正規表現の癖など）を見落とし、
ホワイトボックスだけだと実装のバグをそのまま正解として固定してしまう。

### 0.2 適用する技法

| 技法 | 適用対象 |
|---|---|
| **同値分割** | 入力を「同じ結果になるグループ」に分け、各グループから代表値を1つ選ぶ |
| **境界値分析** | 各グループの境目を狙う。`min-1` / `min` / `max` / `max+1` の4点が基本 |
| **デシジョンテーブル** | 失敗経路が複数ある処理（`decode` など）で、条件の組み合わせを網羅する |
| **状態遷移** | いいね・フォローの ON/OFF と冪等性（6章で扱う） |

### 0.3 表の読み方

| 列 | 意味 |
|---|---|
| **#** | ケース番号。テストコードの `@DisplayName` から参照する |
| **技法** | 同値=同値分割の代表値 / 境界=境界値 / 表=デシジョンテーブル |
| **入力** | 具体的な値。「〜のようなもの」ではなく実際に書ける値にする |
| **期待** | 設計書から導いた期待結果 |
| **根拠** | 設計書の該当箇所。**ここが空欄のケースは仕様の裏付けが無い**ので要注意 |

## 1. CursorCodec

対象: [CursorCodec.java](../backend/src/main/java/com/example/snstimeline/common/CursorCodec.java)
テストクラス: `common/CursorCodecTest`

### 1.1 仕様（ブラックボックス視点）

[05_api_design.md](05_api_design.md) 2.1 より。

| 項目 | 仕様 |
|---|---|
| 形式 | `{"c":"<ISO8601>","i":<id>}` を Base64 エンコードした不透明な文字列 |
| 時刻精度 | **マイクロ秒**（D-33。秒に丸めると同一秒内の投稿を取りこぼす） |
| Base64 | **URLセーフ版**（標準版の `+` がクエリ文字列で空白に化けるため） |
| 不正なカーソル | **400 `VALIDATION_ERROR`** |

### 1.2 encode → decode の往復（正常系）

| # | 技法 | 入力 | 期待 | 根拠 |
|---|---|---|---|---|
| 1 | 同値 | `2026-08-17T12:34:56.123456Z` / id=1234 | decode で同じ値が返る | 05 の 2.1 |
| 2 | 境界 | マイクロ秒が `.000001`（最小の非ゼロ） | **切り捨てられず保持される** | D-33 |
| 3 | 境界 | マイクロ秒が `.999999`（最大） | 保持される | D-33 |
| 4 | 境界 | マイクロ秒が `.000000`（ちょうど秒） | `.000000` として往復する | D-33 |
| 5 | 同値 | `+09:00` のオフセット付き時刻 | **UTCに正規化**され、同じ瞬間を指す | 05 の 2.1 |
| 6 | 境界 | id = `Long.MAX_VALUE` | 往復する | — |
| 7 | 境界 | id = `1`（最小のBIGSERIAL） | 往復する | 04 の 2.1 |

> **#2〜#4 が D-33 の回帰テスト。** 秒精度に戻す変更が入ったら、ここが赤くなる。

### 1.3 URLセーフ性

| # | 技法 | 入力 | 期待 | 根拠 |
|---|---|---|---|---|
| 8 | 同値 | 時刻とidを変えた多数の入力 | 出力に **`+` と `/` が現れない** | 05 の 2.1 |
| 9 | 同値 | 任意の入力 | 出力に **`=`（パディング）が無い** | 05 の 2.1 |

> #8 は「たまたま `+` が出ない入力」で通ってしまわないよう、**パラメータ化テストで多数試す**。
> 1ケースだけでは検証にならない。

### 1.4 decode の失敗経路（デシジョンテーブル）

実装には失敗経路が3つある。**経路と原因を1対1で潰す。**

```
① Base64デコード失敗
② 正規表現 ^\{"c":"([^"]+)","i":(\d+)}$ にマッチしない
③ 日時パース失敗 / Long変換失敗
```

| # | 技法 | 入力 | 通る経路 | 期待 | 根拠 |
|---|---|---|---|---|---|
| 10 | 表 | `"!!!"`（Base64でない） | ① | 400 VALIDATION_ERROR | 05 の 2.1 |
| 11 | 表 | `""`（空文字） | ② | 400 | 05 の 2.1 |
| 12 | 表 | Base64だが中身が `hello` | ② | 400 | 05 の 2.1 |
| 13 | 表 | キー名違い `{"x":"...","i":1}` | ② | 400 | 05 の 2.1 |
| 14 | 表 | id が**負数** `{"c":"...","i":-1}` | ②（`\d+` が符号を弾く） | 400 | ★ |
| 15 | 表 | 前後に**空白** `" eyJ..."` | ① | 400 | ★ |
| 16 | 表 | 日時が `2026-13-45T99:99:99.000000Z` | ③（日時） | 400 | 05 の 2.1 |
| 17 | 表 | id が `99999999999999999999`（long超過） | ③（Long） | 400 | 05 の 2.1 |
| 18 | 表 | 末尾に余分な文字 `{"c":"...","i":1}x` | ②（`$` で弾く） | 400 | ★ |
| 19 | 表 | `null` | 400（NPEにしない） | ★ |

> ★ を付けた #14 #15 #18 #19 は、**表を作って初めて出てきたケース**。
> 実装を眺めるだけでは飛ばしやすい。
>
> **#19 は現在の実装だと NPE になる可能性が高い。** `Base64.getUrlDecoder().decode(null)` は
> `IllegalArgumentException` ではなく `NullPointerException` を投げるため、
> `catch (IllegalArgumentException)` では捕まらず **500 になる**。
> ただし現状 `cursor` が null のときは Service 側が `decode` を呼ばない作りのため、
> **実害は無い**。テストで挙動を確定させ、必要なら実装を直す。

## 6. Service層（LikeService）

対象: [LikeService.java](../backend/src/main/java/com/example/snstimeline/post/LikeService.java)
テストクラス: `post/LikeServiceTest`

### 6.0 部品のテストとの違い

ここから検証の性質が変わる。1〜3章は「入力 → 出力」を見るだけだったが、Service層は
**「何が呼ばれたか／呼ばれなかったか」**を確かめる。ここで初めて **Mockito** を使う。

| | 部品（1〜3章） | Service層（本章） |
|---|---|---|
| 検証対象 | 戻り値 | 戻り値 ＋ **モックへの呼び出し** |
| 主な技法 | 同値分割・境界値 | **状態遷移**・呼び出し検証 |
| 道具 | なし | `verify` / `never()` / `InOrder` |

**モックとは**、本物の代わりに置く偽物のこと。`LikeMapper` は本来DBにアクセスするが、
テストでは偽物に差し替え、「どう呼ばれたか」を記録させる。DBが要らないので**1秒未満で終わる**。

### 6.1 仕様

いいねは**冪等**でなければならない（[06_non_functional.md](06_non_functional.md) 5.3 / D-01）。

> **冪等（べきとう）**: 同じ操作を何回繰り返しても結果が変わらない性質。
> 「いいね」を2回押しても、いいね数は1のまま。通信の再送や連打で数が狂わないために必要。

```
        like()                    like()（2回目は何も起きない）
  ┌──────────────────→ ┌───────────┐
未いいね                 いいね済み ←─┘
  ↑ └───────────────────────┘
  │            unlike()
  └── unlike()（未いいねへの解除も壊れない）
```

実装の要点は**2つのガード**。ここが冪等性を担保している。

```java
public LikeResponse like(Long meId, Long postId) {
  postMapper.findById(postId).orElseThrow(NotFoundException::new);   // 存在チェック

  if (!likeMapper.exists(postId, meId)) {        // ← ガード①（事前SELECT、D-34）
    likeMapper.insert(postId, meId);
    likeMapper.incrementLikeCount(postId);
  }
  return new LikeResponse(likeMapper.findLikeCount(postId), true);   // ← ガードの外側
}

public LikeResponse unlike(Long meId, Long postId) {
  postMapper.findById(postId).orElseThrow(NotFoundException::new);

  int affected = likeMapper.delete(postId, meId);
  if (affected > 0) {                            // ← ガード②（削除件数で判定）
    likeMapper.decrementLikeCount(postId);
  }
  return new LikeResponse(likeMapper.findLikeCount(postId), false);
}
```

### 6.2 冪等性（状態遷移）

**17項目の①②に直接対応する。本章の中核。**

| # | 状態 | 操作 | 期待 | 壊れると何が起きるか | 根拠 |
|---|---|---|---|---|---|
| 54 | 未いいね | like | `insert`・`increment` が**各1回** | いいねが保存されない | 5.3 ① |
| 55 | **いいね済み** | like | **`insert`・`increment` を呼ばない** | **いいね数が2になる** | 5.3 ① / D-34 |
| 56 | いいね済み | unlike | `delete` が1件 → `decrement` が1回 | 解除しても数が減らない | 5.3 ② |
| 57 | **未いいね** | unlike | `delete` が**0件** → **`decrement` を呼ばない** | **数がマイナスになる** | 5.3 ② |

> **#55・#57 が本命。** どちらも「**呼ばれないこと**」の検証で、`verify(mock, never())` を使う。
> 部品のテストには無かった観点。バグは「余計なことをした」ときに起きるため、
> **やっていないことを確かめる**必要がある。

### 6.3 認可・順序

| # | 状態 | 操作 | 期待 | 壊れると何が起きるか | 根拠 |
|---|---|---|---|---|---|
| 58 | 投稿なし | like | **404**。かつ `likeMapper` に**一切触れない** | 存在しない投稿へのゴミデータが残る | D-14 |
| 59 | 投稿なし | unlike | **404**。同上 | 同上 | D-14 |
| 60 | 未いいね | like | **`insert` → `increment` の順** | カウンタだけ増えて実体が無い状態が生じうる | D-01 |

## 8. Service層（PostService）

対象: [PostService.java](../backend/src/main/java/com/example/snstimeline/post/PostService.java)
テストクラス: `post/PostServiceTest`

### 8.1 仕様 — 認可の順序（本章の中心）

[06_non_functional.md](06_non_functional.md) 5.3 の⑦「他人の投稿を削除すると403、存在しない投稿は404」は、
**17項目で唯一「順序が正しいか」と明記された項目**。D-14 の規約そのものである。

```
削除リクエスト
     ↓
① 投稿は存在するか？  ──いいえ──→ 404 NOT_FOUND
     ↓ はい
② 自分の投稿か？      ──いいえ──→ 403 FORBIDDEN
     ↓ はい
③ 削除できたか？      ──いいえ──→ 404（競合。判定後に他の誰かが削除した）
     ↓ はい
   完了
```

> **なぜ順序が重要か。** ①と②を逆にすると、他人の投稿に 403、存在しない投稿に 404 が返るため、
> **「403が返った＝その投稿は実在する」**と分かってしまう。IDを総当たりすれば、
> 見えないはずの投稿の存在を推測できる。これを**情報漏洩**という（D-14）。

**③の競合分岐は `LikeService` に無かった経路。** ①②を通った後、実際に削除するまでの
わずかな間に他の誰かが削除した場合に通る。3分岐すべてをテストする。

### 8.2 投稿の削除（ケース #66〜#70）

## 9. Service層（CommentService）

対象: [CommentService.java](../backend/src/main/java/com/example/snstimeline/comment/CommentService.java)

### 9.1 仕様 — カウンタの非対称ルール

[06_non_functional.md](06_non_functional.md) 5.3 の③④は**対になっている**。

| 操作 | `posts.comment_count` | 理由 |
|---|---|---|
| **コメントを削除** | **-1 する** | コメントが1件減るため |
| **投稿を削除** | **変えない** | コメント自体は論理削除されないため（8.2 #70） |
| **コメントを編集** | **変えない** | 件数は変わらないため |

この非対称さが D-01（非正規化カウンタ）の要点であり、間違えやすいのでテストで固定する。

### 9.2 コメントの削除（ケース #84〜#89）

| # | 状態 | 期待 | 壊れると何が起きるか | 根拠 |
|---|---|---|---|---|
| 84 | コメントなし | **404**。`softDelete` を呼ばない | 存在しないコメントを消そうとする | D-14 ① |
| 85 | **他人のコメント** | **403**。`softDelete` を**呼ばない** | **他人のコメントを削除できてしまう** | 5.3 ⑦ |
| 86 | 自分のコメント | **`decrementCommentCount` が1回** | **削除してもコメント数が減らない** | 5.3 ③ |
| 87 | 削除件数0（競合） | **404**。かつ**カウンタを減らさない** | **消せていないのに数だけ減る** | D-14 ③ |
