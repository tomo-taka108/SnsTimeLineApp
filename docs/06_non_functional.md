# 非機能要件

本書は、機能以外の品質要求を定義する。**学習目的のプロジェクト**であるため、商用サービス相当のSLAや可用性は要求しない（[01_requirements.md](01_requirements.md) 1.2）。

---

## 1. 性能

### 1.1 想定データ量

| 項目 | 想定 |
|---|---|
| ユーザー数 | 100人 |
| 投稿数 | 10,000件 |
| 1ユーザーあたりのフォロー数 | 最大50人 |
| 1投稿あたりのコメント数 | 平均5件、最大100件 |
| 1投稿あたりのいいね数 | 平均10件、最大100件 |
| 画像ファイル | 1件あたり最大5MB、総容量1GB程度 |

この規模なら、[04_data_model.md](04_data_model.md) のインデックス設計で十分に処理できる。

### 1.2 応答時間の目標

| 操作 | 目標 | 備考 |
|---|---|---|
| タイムライン20件の取得（#5） | **1秒以内** | 最も頻繁に呼ばれる。非正規化カウンタとインデックスで達成する |
| 投稿詳細＋コメント20件（#7, #10） | 1秒以内 | |
| 投稿作成（#6） | 1秒以内 | 画像アップロードは別APIなので含まない |
| 画像アップロード（#25） | 5MBで5秒以内 | ネットワーク速度に依存 |
| いいね・フォロー（#14, #21） | 500ms以内 | 楽観的UI更新により体感は即座 |

### 1.3 性能を確保するための設計上の要求

| # | 要求 | 根拠 |
|---|---|---|
| 1 | **タイムライン取得のSQL発行回数は3回以内**（投稿本体 / いいね判定 / 画像） | N+1問題の回避。[04_data_model.md](04_data_model.md) 5.3 |
| 2 | いいね数・コメント数は**都度COUNTしない** | 非正規化カウンタを使う。[04_data_model.md](04_data_model.md) 設計判断① |
| 3 | ページネーションは**カーソル方式**を使う | オフセットは深いページで劣化する。[05_api_design.md](05_api_design.md) 2章 |
| 4 | 一覧の取得件数上限は**50件** | 過大なリクエストを防ぐ |
| 5 | 画像は `Cache-Control: max-age=31536000, immutable` で配信する | 再取得を防ぐ。[05_api_design.md](05_api_design.md) #26 |
| 6 | 画像レスポンスに `width` / `height` を含める | フロントのレイアウトシフト防止 |

### 1.4 性能の検証方法

```sql
EXPLAIN ANALYZE
SELECT p.* FROM posts p
WHERE p.deleted_at IS NULL
ORDER BY p.created_at DESC, p.id DESC
LIMIT 20;
```

**確認すべき点**: `Seq Scan`（全件走査）ではなく `Index Scan` になっていること。`idx_posts_timeline` が使われていること。

> シードデータが少ないとプランナが全件走査を選ぶため、**10,000件程度のダミーデータを投入してから検証する**こと。

## 2. 可用性・運用

| 項目 | 要求 |
|---|---|
| SLA | **定めない**。学習用途のため |
| 稼働時間 | ローカル環境での手動起動を前提とする |
| 冗長化 | 行わない。単一サーバー・単一DB |
| バックアップ | 開発中はDBを作り直せばよい。定期バックアップは不要 |
| 監視 | 行わない |

### 制約: 画像がローカル保存であること

サーバーを別マシンに移すと画像が失われる（[01_requirements.md](01_requirements.md) 8.2）。
これは学習用途として許容するが、**DBには物理パスを保存しない設計**にすることで、S3への移行余地を残している（[04_data_model.md](04_data_model.md) 設計判断⑤、[07_architecture.md](07_architecture.md) 3章）。

## 3. セキュリティ

学習目的でも、**セキュリティの基本は正しく実装する**。誤った実装を身につけないため。

### 3.1 認証・パスワード

| 項目 | 要求 |
|---|---|
| パスワードの保存 | **BCrypt** でハッシュ化する。平文・MD5・SHA-1は使わない |
| BCryptのコスト | 10（Spring Securityの既定値） |
| パスワードの強度 | 8文字以上、英字と数字を各1文字以上（[05_api_design.md](05_api_design.md) #1） |
| ログイン失敗時のメッセージ | **メール未登録とパスワード誤りを区別しない。** 両方 `INVALID_CREDENTIALS` を返す |
| パスワードのログ出力 | **絶対にしない。** リクエストログをとる場合はマスクする |

### 3.2 JWT

| 項目 | 要求 |
|---|---|
| 秘密鍵 | 32バイト以上のランダム文字列。**環境変数 `JWT_SECRET` から読む** |
| 秘密鍵の管理 | ソースコードにハードコードしない。`.gitignore` で `.env` を除外する |
| 署名アルゴリズム | HS256。**`alg: none` を受け入れない**（ライブラリの設定を確認すること） |
| 有効期限 | 24時間。`exp` クレームを必ず検証する |
| ペイロードの内容 | ユーザーIDのみ。**メールアドレスや個人情報を入れない**（JWTはBase64であり暗号化されていない） |

### 3.3 JWTの保管場所（localStorage vs Cookie）

**採用: `localStorage`**（[09_decision_log.md](09_decision_log.md) D-07）

| 保管場所 | メリット | リスク |
|---|---|---|
| **localStorage** | 実装が単純。別オリジンでも `Authorization` ヘッダーで送れる。CSRF対策が不要 | **XSSでトークンを盗まれる** |
| httpOnly Cookie | XSSで読み取れない | **CSRF対策が必須**。別オリジンだと `SameSite` の設定が複雑 |

#### localStorage を選んだ理由と、その前提

学習用途で別オリジン構成のため、実装の単純さを優先した。ただし**XSSリスクを受け入れる代わりに、XSS自体を起こさない実装を徹底する**ことが前提となる。

| # | XSS対策（必須） |
|---|---|
| 1 | **`dangerouslySetInnerHTML` を使わない。** Reactは既定でエスケープするので、通常のJSX描画に徹する |
| 2 | ユーザー入力（投稿本文、自己紹介）をHTMLとして解釈しない |
| 3 | 本文中のURLを自動リンク化する場合、`javascript:` スキームを弾く |
| 4 | 外部ライブラリを増やしすぎない（サプライチェーンリスク） |

> **実務では httpOnly Cookie + CSRFトークンが推奨される。** 本アプリの選択は学習用途の割り切りであり、この判断自体を理解しておくことが重要。

### 3.4 認可

| 項目 | 要求 |
|---|---|
| 他人のリソースの編集・削除 | **403 Forbidden** を返す。[07_architecture.md](07_architecture.md) 4.2 |
| チェック順序 | **① 存在チェック（404） → ② 所有者チェック（403）** の順。逆にすると存在有無が漏れる |
| チェックの実施場所 | **Service層**。Controllerに書くと漏れやすい |
| 対象 | 投稿の編集・削除、コメントの編集・削除、プロフィール編集、`imageFileIds` の所有者 |

> **`imageFileIds` の所有者チェックを忘れやすい**（[05_api_design.md](05_api_design.md) #6）。他人がアップロードした画像を自分の投稿に添付できてしまう。

### 3.5 ファイルアップロード

| 項目 | 要求 |
|---|---|
| 形式の検証 | **拡張子だけでなく、ファイル先頭のマジックナンバーを検証する** |
| 許可形式 | `image/jpeg` / `image/png` / `image/webp` のみ |
| サイズ上限 | 5MB。Spring側の `spring.servlet.multipart.max-file-size` でも制限する |
| 保存ファイル名 | **UUIDを使い、元のファイル名をパスに使わない**（パストラバーサル対策）。[07_architecture.md](07_architecture.md) 3.4 |
| 保存場所 | Webルート外のディレクトリ。**直接静的配信しない**（`GET /files/{id}` 経由で返す） |
| 実行権限 | アップロードディレクトリに実行権限を与えない |

> **拡張子検証だけでは不十分な理由**: `.jpg` にリネームしたスクリプトファイルをアップロードされる可能性がある。先頭バイト（JPEGなら `FF D8 FF`、PNGなら `89 50 4E 47`）を確認する。

### 3.6 SQLインジェクション

| 項目 | 要求 |
|---|---|
| クエリの組み立て | **文字列連結でSQLを作らない。** パラメータバインディングを使う。**MyBatis では値の埋め込みに必ず `#{}` を使い、`${}` は使わない**（`${}` は文字列置換のため、そのままSQLインジェクションになる）。[09_decision_log.md](09_decision_log.md) D-25 |
| ユーザー検索（`LIKE`） | `%` と `_` をエスケープし、`ESCAPE '\'` を付ける。**`q=%` で全ユーザーが列挙されるのを防ぐ。** パラメータバインディングだけでは防げない。[04_data_model.md](04_data_model.md) 6.5 |
| ユーザー検索の対象カラム | **`email` を検索対象にもレスポンスにも含めない。** メールアドレスの存在確認（アカウント列挙）を防ぐ |
| `ORDER BY` の動的指定 | **行わない**（本アプリのソート順は固定なので該当しない） |

### 3.7 CORS

| 項目 | 要求 |
|---|---|
| 許可オリジン | **ワイルドカード `*` を使わない。** 明示的に `http://localhost:5173` を指定 |
| `allowCredentials` | `false`（JWTをヘッダーで送るため）|

詳細は [05_api_design.md](05_api_design.md) 7章。

### 3.8 その他

| 項目 | 要求 |
|---|---|
| エラーメッセージ | **スタックトレースをクライアントに返さない。** `500` では汎用メッセージのみ |
| ログ | パスワード・JWT・個人情報を出力しない |
| 依存ライブラリ | 既知の脆弱性がないバージョンを使う（`mvn dependency-check` 等） |
| HTTPS | 開発環境ではHTTP。本番相当にするなら必須 |
| レート制限 | MVPでは実装しない。[05_api_design.md](05_api_design.md) 8章に候補を記載 |

## 4. 拡張性

学習用途でも「後から変えられる」構造にしておく。

| 拡張ポイント | 現在の設計 | 変更時の作業 |
|---|---|---|
| **画像をS3に移行** | `stored_files` に `storage_type` + `storage_key` を保持 | `S3FileStorageService` を追加し、設定を変えるだけ。[07_architecture.md](07_architecture.md) 3.3 |
| **AWS上で複数台構成にする** | JWTでステートレス、画像は `FileStorageService` 経由、接続先は環境変数 | **アプリ側の変更は不要**。検証結果は [10_infrastructure.md](10_infrastructure.md) 3章 |
| **ユーザー検索を高機能にする** | 前方一致から始め、pg_trgm のインデックスを追加すれば中間一致に拡張できる | クエリの差し替えのみ。[04_data_model.md](04_data_model.md) 6章 |
| **投稿画像を複数枚に** | DBは4枚まで対応済み | APIバリデーションとUIの上限値を変えるだけ。**マイグレーション不要** |
| **コメントに返信を追加** | `parent_comment_id` を追加すれば1階層まで対応可能 | [04_data_model.md](04_data_model.md) 設計判断③ |
| **投稿の編集** | `edited_at` カラムと `PATCH` エンドポイントを設計済み | 実装を足すだけ |
| **退会機能** | `users.deleted_at` を用意済み | |
| **カウンタ方式の変更** | 非正規化カウンタ。再集計SQLを用意済み | 都度COUNTに戻すことも可能 |

> **「今は使わないが、後で必要になったときにマイグレーションが要らない」形にしておく**のが設計の要点。カラムやテーブルを最初から用意しておくコストは低いが、後から追加するコストは高い。

## 5. 保守性

### 5.1 コード規約

| 項目 | 方針 |
|---|---|
| Java | Google Java Style または Spring公式の慣習に従う |
| TypeScript / React | ESLint + Prettier。関数コンポーネント + Hooks |
| 命名 | [08_glossary.md](08_glossary.md) の英語表記に従う。「Tweet」「Fav」などは使わない |
| DTOとドメインモデルの分離 | **ドメインモデル（DBの1行に対応するオブジェクト）をそのままAPIレスポンスにしない。** DTOに詰め替える。`User` は `password_hash` や `email` を持つため、そのまま返すと**秘密情報が漏れる** |
| マジックナンバー | 定数化する。特に文字数上限（280、160、50）は共有定数に（`ValidationConstants`） |

### 5.2 ログ

| レベル | 出力する内容 |
|---|---|
| `ERROR` | 予期しない例外、500エラー |
| `WARN` | 認証失敗、権限エラー（403）、バリデーションエラーの多発 |
| `INFO` | アプリ起動・停止、マイグレーション実行 |
| `DEBUG` | 開発中のSQLログ（MyBatis はMapperのパッケージを `logging.level` で `DEBUG` にすると発行SQLが出る）。**本番相当では無効化** |

**出力してはいけないもの**: パスワード、JWT、メールアドレス。

### 5.3 テスト方針

MVPでは網羅的なテストは求めないが、**以下は必ずテストを書く**。バグが起きたときに原因の特定が難しい箇所である。

| 対象 | テスト内容 | 理由 |
|---|---|---|
| **いいねの冪等性** | 同じ投稿に2回いいねしてもカウンタが2にならない | [04_data_model.md](04_data_model.md) 設計判断①の要 |
| **いいね解除の冪等性** | いいねしていない状態で解除しても壊れない | |
| **コメント削除時のカウンタ** | コメントを論理削除すると `comment_count` が -1 される | 非対称ルール（設計判断②）を守れているか |
| **投稿削除時のカウンタ** | 投稿を論理削除しても `comment_count` は変わらない | 上と対になる確認 |
| **論理削除の除外** | 削除済み投稿がタイムラインに出ない、GETで404になる | 全クエリに `deleted_at IS NULL` が付いているか |
| **自己フォローの拒否** | 自分をフォローすると400 | |
| **他人のリソース操作** | 他人の投稿を削除すると403、存在しない投稿は404 | 順序が正しいか |
| **カーソルページネーション** | **同一 `created_at` の投稿が2件あっても取りこぼさない** | タイブレーカーが効いているか |
| **ファイル所有者チェック** | 他人の `fileId` を指定した投稿が403になる | 見落としやすい |

> **カーソルページネーションのテストには、同一 `created_at` の投稿を含むシードデータが必要**（[04_data_model.md](04_data_model.md) 7章）。

### 5.4 ドキュメントの保守

| 項目 | 方針 |
|---|---|
| 実装がドキュメントと乖離した場合 | **ドキュメントを更新する。** 乖離を放置しない |
| 設計を変更した場合 | [09_decision_log.md](09_decision_log.md) に理由を記録する |
| 機能を追加した場合 | [02_feature_list.md](02_feature_list.md) に機能IDを採番して追加。関連画面・APIの列も埋める |

## 6. ユーザビリティ

### 6.1 対応ブラウザ

| ブラウザ | バージョン |
|---|---|
| Chrome / Edge | 最新版 |
| Firefox | 最新版 |
| Safari | 最新版（macOS / iOS） |

Internet Explorerは対象外。

### 6.2 レスポンシブ対応

| 画面幅 | 対応 |
|---|---|
| 375px〜（スマートフォン） | 1カラム。すべての機能が利用できる |
| 768px〜（タブレット / PC） | 最大幅600pxで中央寄せ |

詳細は [03_screen_design.md](03_screen_design.md) 4.2。

### 6.3 アクセシビリティ（最低ライン）

網羅的な対応は求めないが、以下は満たす。

| # | 項目 |
|---|---|
| 1 | 画像に `alt` 属性を付ける（投稿画像は投稿本文を、アバターは表示名を使う） |
| 2 | ボタン・リンクをキーボードで操作できる（`div` に `onClick` を付けただけの疑似ボタンを作らない） |
| 3 | フォームの入力欄に `<label>` を関連付ける |
| 4 | いいねボタンの状態を `aria-pressed` で表現する |
| 5 | 色のコントラスト比を4.5:1以上にする |
| 6 | **情報を色だけで伝えない**（いいね済みは色＋塗りつぶしの形状で示す） |

### 6.4 応答性の体感

| 項目 | 方針 |
|---|---|
| いいね・フォロー | **楽観的UI更新**で即座に反映し、サーバー応答で補正する（[03_screen_design.md](03_screen_design.md) SC-03） |
| 一覧のローディング | スピナーではなく**スケルトン**を使い、レイアウトシフトを防ぐ |
| 画像 | `width` / `height` で領域を先に確保する |
| 投稿作成 | モーダルを閉じてタイムライン先頭に即座に挿入する |

## 7. 非機能要件のチェックリスト

実装完了時に確認する。

### 性能
- [ ] タイムライン20件の取得が1秒以内
- [ ] タイムライン取得のSQL発行が3回以内（N+1が起きていない）
- [ ] `EXPLAIN ANALYZE` で `Index Scan` が使われている（10,000件のデータで検証）

### セキュリティ
- [ ] パスワードがBCryptでハッシュ化されている（DBを直接見て平文がないことを確認）
- [ ] `JWT_SECRET` が環境変数から読まれ、リポジトリにコミットされていない
- [ ] `.env` と `uploads/` が `.gitignore` に含まれている
- [ ] ログイン失敗時にメール未登録とパスワード誤りが区別されない
- [ ] 他人の投稿を削除すると403、存在しない投稿は404（順序が正しい）
- [ ] 他人の `fileId` を指定した投稿が403で拒否される
- [ ] 拡張子を偽装したファイルがマジックナンバー検証で拒否される
- [ ] CORSの許可オリジンがワイルドカードでない
- [ ] 500エラーでスタックトレースが返らない

### 拡張性
- [ ] `stored_files` に絶対URLも物理パスも保存されていない
- [ ] `FileStorageService` がインターフェースとして定義され、Service層が実装クラスに直接依存していない

### 保守性
- [ ] 5.3のテスト項目がすべて実装されている
- [ ] ドメインモデルがそのままAPIレスポンスになっていない（DTOに詰め替えている）
- [ ] MyBatis の値の埋め込みが `#{}` になっている（`${}` を使っていない）

### ユーザビリティ
- [ ] スマートフォン幅（375px）で全機能が使える
- [ ] 一覧の4状態（ローディング / 空 / エラー / 正常）がすべて実装されている
- [ ] いいね済みが色だけでなく形状でも判別できる
