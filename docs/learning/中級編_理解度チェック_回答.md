### Q1. セッション認証とトークン認証

> 「セッション認証」と「トークン（JWT）認証」の違いを説明してください。
> 
> 
> また、このアプリでJWTを採用した理由（利点）も述べてください。
> 

**回答:**
「セッション認証」
ログイン成功時、サーバーが「セッションID」を発行してサーバー側のメモリやDBに保存し、同じIDをクッキーとしてブラウザに渡す。以降のリクエストではブラウザが自動でそのクッキーを送り、サーバーは受け取ったIDを自分の保存領域と照合して「誰か」を判定する。サーバーが認証状態を持つ（ステートフル）。
「トークン（JWT）認証」
ログイン成功時、サーバーがユーザー情報を含む署名付きトークン（JWT）を発行してブラウザに渡す。ブラウザはそれを保持し、以降のリクエストで（通常は Authorization ヘッダに載せて）送る。サーバーは保存領域と照合せず、トークンの署名を検証するだけで正当性を確認できる。サーバーは認証状態を持たない（ステートレス）。

このアプリでJWTを採用した理由
- サーバーがセッションを保持しないため、サーバーを複数台に増やしても（水平スケール）どのサーバーが受けても認証できる（セッション方式だと「どのサーバーにログインしたか」を揃える仕組みが別途必要になる）
- 検証がDB照会ではなく署名検証（計算処理）で完結するため、リクエストごとにDBへ問い合わせる必要がない

### Q2. アクセストークンとリフレッシュトークン

> 以下について説明してください：
> 
- なぜトークンを2種類に分けるのか
- アクセストークンの有効期限が短い理由

（アクセストークン: 15分 / リフレッシュトークン: 7日）

**回答:**
「なぜトークンを2種類に分けるのか」
「短命にして漏洩時の被害を抑えたい」のと「毎回ログインし直すのは不便」という相反する要求があり、1種類のトークンでは両立できない。そこで役割を分ける。
- アクセストークン：実際のAPIリクエストのたびに送る入場券。短命にして、盗まれても被害を小さく抑える
- リフレッシュトークン：アクセストークンの再発行専用。APIには使わず送信頻度が低いため、露出機会が少なく、長命でもリスクが小さい

こうして「頻繁に使うが被害範囲は狭いトークン」と「使用頻度は低いが強力なトークン」に分けることで、利便性と安全性を両立させている。

「アクセストークンの有効期限が短い理由」
アクセストークンは毎リクエストで送信されるため、通信経路やブラウザ上に露出する機会が最も多く、盗まれるリスクが一番高い。仮に盗まれても15分で失効すれば、悪用できる時間を短く抑えられる。

### Q3. パスワードのハッシュ化

> 「ハッシュ化」と「暗号化」の違いを説明してください。
> 
> 
> また、なぜパスワード保存にハッシュ化を使うのか述べてください。
> 

**回答:**
「ハッシュ化」
元のデータ（生のパスワード）を、一定の計算（ハッシュ関数）によって固定長の意味のない文字列に変換すること。不可逆であり、ハッシュ化した文字列から元のパスワードに戻すことはできない。同じ入力からは必ず同じ出力になるため、ログイン時は「入力されたパスワードを同じ方法でハッシュ化し、保存済みのハッシュ値と一致するか」で照合する。

「暗号化」
元のデータを、鍵を使って別の形式に変換すること。可逆であり、対応する鍵を使えば元のデータに戻せる（復号）。通信の暗号化（HTTPS）やファイルの暗号化のように、「後で元に戻す必要があるデータ」に使う。

両者の違いの軸は「元に戻す必要があるかどうか」。パスワードはサーバー側が元の値を知る必要が一切ない（照合できればよい）ため不可逆なハッシュ化を使い、通信内容のように受け取った側が元に戻して読む必要があるものには可逆な暗号化を使う。

「なぜパスワード保存にハッシュ化を使うのか」
生のパスワードやそれを復号可能な形で保存すると、DBが漏洩した際にすべてのユーザーの生パスワードがそのまま流出する。ハッシュ化して保存しておけば、漏洩してもハッシュ値から元のパスワードを計算で導き出すことはできず、被害を抑えられる。

### Q4. 認可（Authorization）

> 「認証」と「認可」の違いを説明し、
> 
> 
> 「自分の投稿のみ編集・削除できる」機能がどちらに該当するか答えてください。
> 

**回答:**
「認証（Authentication）」
「あなたは誰か」を確認すること。今回のアプリでは、メールアドレス＋パスワードでログインし、正しい本人であることを確認する処理。結果として「ログインできているか（＝誰であるか）」が分かる。

「認可（Authorization）」
「その人に、その操作を行う権限があるか」を確認すること。認証で「誰であるか」が分かった後、その人が要求している操作（編集・削除・閲覧など）を許可してよいかを判定する処理。

「自分の投稿のみ編集・削除できる」機能はどちらに該当するか
認可に該当する。ログインしているだけ（認証済み）では誰の投稿でも編集できてしまうため、「操作対象の投稿の author_id と、リクエストしてきたユーザーのIDが一致するか」を追加でチェックする必要がある。この所有者チェックが認可の役割そのもの。

なお、このアプリでは「存在チェック→404、所有者チェック→403」の順序を守っている（D-14）。存在しない投稿に先に所有者チェックをしてしまうと、「403が返る＝投稿は存在するが他人のもの」という情報が漏れてしまうため。

### Q5. CORS設定の実務理解

> 以下について説明してください：
> 
- 本番環境でのCORS設定の変更点
- `allowedOrigins("*")`の問題点

**回答:**
前提として、ブラウザには「あるオリジン（プロトコル＋ドメイン＋ポートの組み合わせ）から読み込んだJavaScriptは、別のオリジンにリクエストを送ることを原則禁止する」という同一オリジンポリシーがある。CORS（Cross-Origin Resource Sharing）は、サーバー側が「このオリジンからのリクエストは許可する」と明示することで、この制限を例外的に解除する仕組み。開発環境ではフロント（localhost:5173）とバック（localhost:8080）がポート違いで別オリジンになるため、CORS設定が必須になる。

「本番環境でのCORS設定の変更点」
開発環境では http://localhost:5173 を許可オリジンに設定しているが、本番環境ではフロントを配信する実際のドメイン（例: https://sns-timeline.example.com）に変更する必要がある。このアプリでは .env の CORS_ALLOWED_ORIGINS を環境ごとに切り替えることでこれに対応している（開発中は localhost、本番ではデプロイ先の本番ドメインを設定する）。

「allowedOrigins("*")の問題点」
CORSの役割は「このAPIのレスポンスを、どのオリジンのJavaScriptに読ませてよいか」をブラウザに指定すること。* にすると、世界中のどのWebサイトが作ったJavaScriptからでも、このAPIを呼んでレスポンス（投稿データやプロフィール情報など）を読み取れてしまう。たとえば悪意のあるサイトが、訪問者のブラウザに仕込んだスクリプトで裏側からこのAPIを呼び、返ってきたデータを盗み見る、といったことが技術的に可能になる。本来このAPIを呼んでよいのは自分のフロントエンド（決まったドメイン）だけのはずなので、許可オリジンは限定するべきであり、* は実務では使うべきではない設定になっている。

### Q6. SQLインジェクション

> SQLインジェクションとは何か説明してください。
> 
> 
> また、MyBatisで防ぐための実装上の注意点を述べてください。
> 

**回答:**
「SQLインジェクションとは」
ユーザーが入力した文字列を、そのままSQLの命令文にくっつけてしまうことで、想定外のSQLが実行されてしまう攻撃。例えば WHERE email = '" + email + "' のように文字列をつなげてSQLを作っていると、emailの欄に ' OR '1'='1 のような特殊な文字列を入力されただけで、条件が常に成立してしまい、パスワードが分からなくてもログインできてしまう。本来「ただの入力値」であるはずのものが、SQLの一部として解釈されてしまうのが原因。

「MyBatisで防ぐための実装上の注意点」
値をSQLに渡すときは、必ず #{} を使う。#{} を使うと、値は「あくまで1つのデータ」として安全に渡され、中に特殊な文字が入っていてもSQLの構造そのものが書き換わることはない。

一方 ${} は入力された文字列をそのままSQL文に貼り付けてしまう書き方のため、これを使うとSQLインジェクションが起きてしまう。${} はテーブル名やカラム名を状況に応じて切り替えたいときなど特別な場合だけに使い、ユーザーの入力値を直接渡すことは絶対にしない。

### Q7. XSS（クロスサイトスクリプティング）

> 以下について説明してください：
> 
- `<script>alert('攻撃')</script>` が投稿された場合のリスク
- Reactでの対策方法

**回答:**
「XSSとは」
ユーザーが入力した内容が「ただの文字列」として表示されるべきところを、「JavaScriptのプログラム」として実行されてしまう攻撃。

「<script>alert('攻撃')</script> が投稿された場合のリスク」
例えばコメント欄に攻撃者がこの文字列を投稿し、それがそのままHTMLとして画面に埋め込まれてしまうと、後からそのコメントを閲覧した別のユーザーのブラウザ上でこのスクリプトが実行される。単なるポップアップ表示なら実害は少ないが、実際の攻撃ではもっと悪質なことができてしまう。
- localStorage に保存されたJWT（アクセストークン・リフレッシュトークン）を盗み出し、攻撃者のサーバーに送信する → 盗まれたトークンでなりすましログインされる
- 悪意のあるサイトへ強制的にリダイレクトさせる
- 画面上に偽のログインフォームを表示して認証情報を盗む（フィッシング）

このアプリはJWTをlocalStorageに保存する方式（D-07）のため、XSSが成立すると即座にアカウント乗っ取りにつながるという点で特にリスクが高い。

「Reactでの対策方法」
Reactは <p>{review.comment}</p> のようにJSXの {} で値を埋め込むと、その値を常に文字列として扱い、DOMに挿入する際もHTMLとして解釈しない。そのため <script> タグが含まれていても、タグとして実行されず、画面上にはそのままの文字列として表示される。これはReactがデフォルトでエスケープ処理を自動的に行っているためであり、開発者が個別に対策を書く必要がない。

### Q8. HTTPSと本番セキュリティ

> 以下について説明してください：
> 
- ALBを使った場合のSSL/TLS証明書の配置場所
- ALB〜バックエンド間通信のHTTPS必要性

**回答:**
「ALBを使った場合のSSL/TLS証明書の配置場所」
SSL/TLS証明書はEC2（アプリ本体）ではなく、ALBに配置する。ALBはブラウザからのリクエストを最初に受け取る中継役であり、ここでHTTPS通信の受け口を一手に引き受ける。証明書をALBに集約することで、EC2サーバーを複数台に増やしても、それぞれに証明書を設定・更新する手間がかからず、有効期限の管理もALB側だけで済む。

「ALB〜バックエンド間通信のHTTPS必要性」
ユーザーのブラウザとALBの間は公衆インターネットを通るため、HTTPSによる暗号化は必須。一方でALBとEC2の間は、AWSのプライベートネットワーク（VPC内）に閉じた通信であり、外部から直接到達できないため、通信内容が盗聴されるリスクは比較的低い。そのため実務では、この区間はHTTPのまま運用し、証明書管理の手間や処理負荷を省く選択も取られる。

ただしこのアプリはメールアドレス・パスワードという認証情報を扱うため、内部ネットワークであっても信頼しすぎない「ゼロトラスト」の考え方に立つなら、ALB〜EC2間もHTTPS化する選択肢がある。どちらを選ぶかは、セキュリティ要件の厳しさと運用コストのバランスで判断する。

### Q9. レイヤードアーキテクチャ

> Controller / Service / Repository の役割を説明してください。
> 
> 
> また、以下も答えてください：
> 
- なぜ分離するのか
- ControllerとServiceの責務の境界

**回答:**
「Controller / Service / Repository の役割」
- Controller：HTTPリクエストとレスポンスの窓口。URLパスに対応するメソッドを受け、リクエストの内容（パスパラメータ・クエリ・ボディ）を受け取り、Serviceを呼び出した結果をHTTPレスポンス（JSON・ステータスコード）に変換して返す
- Service：業務ロジック（ビジネスルール）を処理する層。「いいねの冪等性を保つ」「他人の投稿は編集できないようにする」といった、今回のアプリ固有のルールもここに書く。
- Repository：DBへのアクセス窓口。SQL（今回のアプリではMyBatisのMapper）を実行し、データの取得・保存だけを担当する。業務ルールの判断はここには書かない

「なぜ分離するのか」
- 責務を分けることで、変更の影響範囲が閉じ込められる。例えばDBをPostgreSQLから別のDBに変えたい場合、Repository層だけを直せばよく、ServiceやControllerには影響しない
- テストがしやすくなる。Serviceだけを単体でテストしたい場合、Repositoryを偽物（モック）に差し替えれば、実際のDBを使わずにロジックだけを検証できる
- 層ごとに責務が明確なら、不具合が起きたときも「HTTPの形式がおかしい→Controller」「業務ルールがおかしい→Service」「データが壊れている→Repository」と、問題の切り分けがしやすくなる

「ControllerとServiceの責務の境界」
Controllerは「業務ロジックを持たない」のが境界線。Controllerに書いてよいのは、リクエストの形式チェック（バリデーション）・Serviceの呼び出し・結果をHTTPレスポンスに変換する処理のみで、「いいねが既に押されているかどうかの判定」のような業務上の意思決定はServiceの責務。

### Q10. DTOパターン

> エンティティを直接APIに使わない理由を説明してください。
> 

**回答:**
エンティティはDBのテーブルの1行を、そのままJavaのオブジェクトとして表現したクラス。テーブルの全カラムに対応するフィールドを持つ。

エンティティを直接APIに使わない理由は大きく2つある。

1つ目は、DBの変更に対する影響範囲を小さくするため。DTOを挟まずエンティティを直接APIレスポンスに使っていると、DB側でカラム名を変更した場合、そのままAPIレスポンスの形も変わってしまい、それを使っているフロントエンドなどのクライアント側の修正まで必要になる。DTOを挟んでおけば、変更が必要な箇所は「エンティティ」と「エンティティ→DTOへの変換処理」のサーバー内部2箇所だけで済み、DTOの形（＝APIの契約）自体は変えずに済むため、フロントエンドは何も直さなくてよい。実務では同じAPIを複数のクライアント（Webフロント、スマホアプリ、他チームの別画面など）が使うことも多く、影響範囲が広がるほどこの差は大きくなる。

2つ目は、不要な情報や機密情報を漏らさないため。エンティティをそのままAPIレスポンスに使うと、例えばこのアプリのusersテーブルが持つpassword（ハッシュ値）やemailまでクライアントに送信されてしまう。DTOを挟むことで、返してよいフィールドだけを明示的に選んで公開できる。

### Q11. グローバル例外ハンドリング

> 各Controllerでtry-catchする場合と比較した利点を説明してください。
> 

**回答:**
各Controllerで個別にtry-catchすると、以下の問題が起きる。
- 同じようなエラーハンドリングのコードが、Controllerの数だけ重複してしまう。「予期しない例外が起きたら500エラーとしてErrorResponseを返す」といった処理を、投稿・コメント・いいね・フォローなど、すべてのControllerに毎回書くことになる
- 書き忘れが起きる。try-catchを書き忘れたControllerだけ、エラー時に想定外のレスポンス（スタックトレースがそのまま返る等）になってしまうリスクがある

@RestControllerAdvice を使ったグローバル例外ハンドリング（このアプリではGlobalExceptionHandler）を使うと、例外の種類ごとの処理を1箇所にまとめられる。これにより、
- 重複コードがなくなり、修正が1箇所で済む。例えばエラーレスポンスの形式を変えたい場合、全Controllerを直す必要がなく、GlobalExceptionHandlerだけ直せばよい
- 書き忘れが起きない。Controller側は業務処理だけに集中でき、例外が発生すればSpringが自動的にGlobalExceptionHandlerに処理を委譲してくれるため、個々のControllerでエラーハンドリングを意識する必要がない
- Controllerのコードが業務ロジックの呼び出しだけになり、可読性が上がる

### Q12. MyBatis vs JPA

> 以下の観点で違いを説明してください：
> 
- SQL制御
- 学習コスト

**回答:**
「SQL制御」
- MyBatis：SQLを直接、自分でXML（またはアノテーション）に書く。実行されるSQLがそのまま目に見えるため、細かいチューニング（インデックスを使わせる書き方、複雑なJOIN、N+1を避ける一括取得など）を自分で完全にコントロールできる
- JPA：エンティティに対する操作（save、findById など）を書くと、JPAが自動でSQLを生成して実行する。開発者は基本的にSQLを直接書かない（複雑なクエリではJPQLや@Queryを書くこともある）。生成されるSQLがどうなるかはJPA任せになるため、意図しないSQL（想定外のJOINやN+1）が発行されることがある

「学習コスト」
- MyBatis：SQL自体は既に知っている人にとっては学習コストが低い。新しく覚える概念が少なく、書いたSQLがそのまま動くため直感的。ただし、DBの設計やSQLの知識がまだ浅い人には、SQLを都度書く分の負担がある
- JPA：SQLを意識せずにコードが書けるため、最初のハードルは低く見える。しかし裏側の仕組み（Hibernateの遅延ロード、N+1問題、キャッシュ、@OneToManyなどのマッピング）を正しく理解していないと、思わぬバグや性能問題を踏みやすい。「動くコードは書けるが、なぜそう動くのか理解するのに時間がかかる」ため、きちんと使いこなすための学習コストはむしろ高いとされることが多い

つまり、「入り口の分かりやすさ」ではJPAが低く見えるが、「事故なく使いこなすまでの学習コスト」で見るとJPAの方が高い、という逆転が起きやすい分野である。

このアプリがMyBatisを採用した理由は、MyBatisは値の埋め込みに#{}を使う限りSQLインジェクションを防げる上、実行されるSQLが常に明示的で、N+1問題やマッピング漏れを起こしにくいという判断（D-25）による。

### Q13. 環境ごとの設定管理

> プロファイルの仕組みと、環境ごとに設定を分ける理由を説明してください。
> 

**回答:**
「プロファイルの仕組み」
ソフトウェア開発では、「開発中に使う環境」と「実際にユーザーが使う本番環境」など、複数の環境を使い分けるのが一般的。プロファイルとは、その環境ごとに異なる設定値をひとまとめにし、起動時に切り替えられるようにする仕組みのこと。

Spring Bootでは、共通設定をapplication.ymlに書きつつ、application-dev.yml（開発用）やapplication-prod.yml（本番用）のように環境別のファイルを用意し、起動時にどのプロファイルを有効にするか（SPRING_PROFILES_ACTIVE=prod など）を指定することで、DB接続先やログレベルといった値を環境ごとに自動で切り替えられる。

「環境ごとに設定を分ける理由」
複数の環境を扱う以上、環境ごとに設定を分けないと以下のような問題が起きる。
- 誤操作による事故が起きやすくなる。設定が1つしかないと、開発中に間違えて本番DBに接続してテストデータを流し込んでしまう、といった事故が起こり得る
- 環境ごとに適切な挙動が異なる。例えば開発環境ではエラーの詳細（スタックトレース）を画面に出したいが、本番環境ではセキュリティ上出したくない等。ログレベルも開発ではDEBUG、本番ではINFOに絞りたい、といった違いがある
- 機密情報を安全に扱えなくなる。JWT_SECRETやDBパスワードのような値をソースコードに直接書かず、環境ごとに異なる値を環境変数として注入することで、コードと機密情報を分離できる

### Q14. Flyway（DBマイグレーション）

> マイグレーションツールを使う理由を説明してください。
> 
> 
> （直接ALTER TABLEしない理由）
> 

**回答:**
「マイグレーションツールとは」
DBのテーブル構造（スキーマ）の変更を、SQLファイルなどの「変更履歴」として1つずつバージョン管理し、順番に適用していく仕組みを持つツール。Flywayはその代表例で、例えばV1__create_users.sql、V2__create_refresh_tokens.sqlのように、バージョン番号付きのSQLファイルをdb/migration配下に置いておき、アプリ起動時にFlywayが未適用のファイルだけを検出して自動的に順番に実行する。

「マイグレーションツールを使う理由（直接ALTER TABLEしない理由）」
DBの構造変更を、開発者がその場で手動でALTER TABLEを実行して行うと、以下の問題が起きる。
- 環境ごとにDBの状態がズレる。開発者Aのローカル、開発者Bのローカル、本番環境で、それぞれ手動でSQLを実行していると、誰かが1つ実行し忘れる・順番を間違えるといったミスが起こりやすく、気づかないうちに環境ごとにテーブル構造が食い違ってしまう
- 変更履歴が残らない。「いつ・誰が・どんな理由でこのカラムを追加したのか」が、手動実行では記録に残らない。SQLをファイルとして残しておけば、それ自体が変更履歴になり、Gitの履歴とも紐づけられる
- 再現性がない。新しく開発に参加した人や、新しいサーバーを立てるときに、「最初から今のDB構造をどう作ればいいか」を手動で再現するのは非常に手間がかかる。マイグレーションツールを使えば、未適用のファイルを順番に流すだけで、誰の環境でも同じDB構造を機械的に再現できる

Flywayは、実行済みのマイグレーションを管理用テーブル（flyway_schema_history）で記録しており、アプリ起動のたびに「まだ適用していないファイルだけ」を自動で検出して実行する。

なお、一度適用したマイグレーションファイルは、後から編集してはいけない。編集するとチェックサムが一致せず起動時にエラーになるため、修正は必ず新しいバージョンのファイル（V10__... など）を追加する形で行う。

### Q15. Axiosインターセプター

> インターセプターとは何か説明してください。
> 
> 
> また、これが無い場合の問題点も述べてください。
> 

**回答:**
「インターセプターとは」
HTTPクライアントライブラリが提供する、リクエストを送る前／レスポンスを受け取った後に、共通処理を差し込める仕組み。個々のAPI呼び出しのたびに同じ処理を書かなくても、1箇所に登録しておけば全リクエストに自動で適用される。Axiosではaxios.interceptors.request.use(...)（送信前）とaxios.interceptors.response.use(...)（受信後）という形で登録する。典型的な用途は、認証トークンの自動付与、ログ出力、処理時間の計測、401受信時の自動リトライなど。

「これが無い場合の問題点」
インターセプターが無いと、これらの共通処理を個々のAPI呼び出し箇所すべてに、その都度書くことになる。結果として、
- コードが重複し、修正が必要になったときに全箇所を直す必要がある
- 書き忘れが起きる。例えばあるAPI呼び出しだけ認証トークンを付け忘れる、401時の再ログイン処理を書き忘れる、といったミスが起きやすい

### Q16. React Context

> なぜpropsではなくContextが選ばれたのか説明してください。
> 
> 
> また、適切なケース / 不適切なケースも述べてください。
> 

**回答:**
「propsとContextの違い」
コンポーネント間でデータを受け渡す方法にはいくつかあるが、代表的なのがpropsとContext。
- props：親コンポーネントから子コンポーネントへ、明示的にデータを渡していく方式。子がさらに孫に渡す必要があれば、間の層すべてでそのデータを受け取って次に渡す、という記述が必要になる
- Context：あらかじめデータを登録する場所（Provider）を作っておくと、その配下にあるどのコンポーネントからでも、階層の深さに関係なく直接データを取り出せる仕組み

「なぜpropsではなくContextが選ばれたのか」
コンポーネントの階層が深い場合、propsだけで値を渡そうとすると、その値を使わない中間のコンポーネントにも、ただ中継するためだけの記述が必要になってしまう（これを「プロップドリリング」と呼ぶ）。階層が増えるほど、中間コンポーネントの数だけ記述が増え、コードが複雑になる。

Contextを使えば、値を実際に使うコンポーネントだけが直接値を取得すればよく、中間のコンポーネントは一切関与する必要がない。例えば、ログイン中のユーザー情報やログイン状態のように、アプリのほぼ全体（多くの画面・多くの階層）で参照される値にContext（AuthContext）を使う。

「適切なケース」
コンポーネントの階層が深く、多くの離れた場所から同じデータを参照する必要がある場合（例: ログイン中のユーザー情報、テーマ設定など、アプリ全体に関わる状態）

「不適切なケース」
- コンポーネントの階層が浅く、親から子への受け渡しで十分な場合。Contextを使うと、どこからその値が来ているのか追いにくくなり、かえってコードの見通しが悪くなる
- 頻繁に値が更新される状態をContextに乗せると、Contextの値を参照しているコンポーネントがProvider配下全体で再レンダリングされてしまい、パフォーマンスに悪影響が出やすい。例えば入力フォームの1文字ごとの値のような、狭い範囲かつ高頻度で更新される値には向かない

### Q17. カスタムフック

> なぜロジックをコンポーネントではなくフックに分離するのか説明してください。
> 

**回答:**
「前提：コンポーネントとフックの役割」
Reactのコンポーネントは、本来「見た目（JSX）を組み立てて返す」ことが主な役割。しかし実際には、状態管理（useState）やAPI呼び出し（useEffect）といったUIロジックもコンポーネントの中に書けてしまう。

「カスタムフックとは」
useから始まる関数として、状態管理やAPI呼び出しなどのUIロジックだけを切り出し、再利用可能な形でコンポーネントの外に独立させたもの。JSX（見た目）は返さず、値や関数だけを返す。

「なぜロジックをコンポーネントではなくフックに分離するのか」
UIロジックをコンポーネントの中に書き続けると、以下の問題が起きる。
- コンポーネントが肥大化し、見た目とロジックが混ざって読みにくくなる。「画面がどう見えるか」を追いたいだけなのに、間にAPI呼び出しやデバウンス処理のコードが挟まり、JSXの見通しが悪くなる
- 同じロジックを別の画面で使い回せない。ロジックがコンポーネントに埋め込まれていると、似たような処理が必要になったときにコピペするしかなくなる
- ロジック単体のテストがしにくい。見た目とUIロジックが一体になっていると、UIロジックだけを検証したくても画面の描画ごとテストする必要が出てくる

カスタムフックに分離すると、これらが解決する。「見た目の組み立て（コンポーネント）」と「状態・UIロジック（フック）」を役割ごとに分けられ、ロジックだけを再利用・単体テストできるようになる。

### Q18. コンポーネント設計

> 良いコンポーネント分割とは何か、具体例を挙げて説明してください。
> 

**回答:**
「良いコンポーネント分割とは」
コンポーネント分割の基準は、大きく2つの観点がある。
1. 再利用性：複数の画面・場所で同じ見た目・同じ動きが必要になる部分は、独立した共通コンポーネントとして切り出す
2. 単一責任：1つのコンポーネントが担う役割を、できるだけ1つに絞る。「見た目の表示」と「データの取得・状態管理」のように、性質の異なる責務を1つの巨大なコンポーネントに詰め込まない（Q17のカスタムフックの分離と同じ考え方）

良い分割ができていると、1つのコンポーネントを見れば「これが何をするものか」が一目で分かり、変更が必要なときも影響範囲が閉じ込められる。逆に分割が悪いと、1つの巨大なコンポーネントがあらゆる責務を抱え込み、少し直すだけで別の画面まで壊れる、という事態が起きる。

「具体例（今回のSnsTimeLineアプリの場合）」
- 共通コンポーネント（再利用性の観点）：AppHeader（全画面共通のヘッダー）、UserRow（ユーザー一覧の1行を表示する部品。検索結果一覧・フォロー一覧・フォロワー一覧など複数の画面で使い回されている）、Pagination（ページ送りのUI）のように、複数の画面で同じ見た目・同じ動きをする部品を独立させている
- 画面固有のコンポーネント（責務の分離の観点）：SearchPage（画面全体の組み立てとJSX）とuseUserSearch（検索のロジック）を分けているように、同じ「ユーザー検索」という機能の中でも、見た目とロジックという異なる責務ごとに分割している

補足として、AppHeaderはメニュー開閉などの簡単なロジック（isOpen等）を自身の中に持っており、UIロジックを常に別ファイルのフックへ分離するわけではない。ロジックが複雑・複数箇所で再利用したい・単体テストしたい場合にフックへ分離し、単純で1箇所でしか使わないロジックはコンポーネント内に留める、という判断がこのアプリ全体で一貫している。

### Q19. TypeScriptの型安全性

> 型のメリットと、AIコードレビュー時の利点を説明してください。
> 

**回答:**
「型のメリット」
TypeScriptでは、変数・関数の引数・戻り値などに「型」（数値・文字列・特定の形をしたオブジェクトなど）を明示的に定義できる。これにより、意図しない値を代入しようとしたときに、エラーとして検出できる。

ここで重要なのは、「いつ」検出できるかという点。型エラーはコードを実行する前（コンパイル時・エディタ上で書いている最中）に検出できる。例えばJavaScriptのように型のない言語だと、「本当は数値が来るはずの変数に文字列が入っていた」というミスは、実際にそのコードが実行されるまで気づけない（実行時エラー）。TypeScriptなら、その場でエディタが赤い波線を出して知らせてくれるため、バグを本番に届く前に潰せる。

「AIコードレビュー時の利点」
型定義は、人間だけでなくAIにとっても「このコードが何を期待しているか」を厳密に伝える仕様書として機能する。
- 型が明示されていれば、AIは「この関数はこういう値を受け取り、こういう値を返すべきだ」という前提をコードから直接読み取れるため、その前提と矛盾するコード（渡している値の型が違う、必須フィールドが欠けている等）を高い精度で指摘できる
- 逆に型が無い（またはゆるい）コードでは、AIも人間と同様に「この変数には本当は何が入る想定なのか」をコメントや変数名から推測するしかなく、指摘の精度が下がる

つまり型は、「意図」をコードそのものに埋め込む手段であり、それが厳密であるほど、人間・AIどちらにとっても「意図とズレたコード」を機械的に検出しやすくなる。

### Q20. SPAルーティング

> 従来のWebとの違いを説明し、
> 
> 
> 「直接URLで404になる問題」の原因と対策を述べてください。
> 

**回答:**
「従来のWeb（MPA）とSPAの違い」
従来型のWebアプリケーション（MPA: Multi Page Application）は、画面遷移のたびにサーバーへリクエストを送り、サーバーが新しいHTMLページ全体を生成して返す仕組み。リンクをクリックするたびにページ全体が真っ白になって再読み込みされる。

SPA（Single Page Application）は、最初に1枚だけHTMLを読み込み、以降の画面遷移はJavaScript（React Router等）がブラウザ内でDOMを書き換えるだけで実現する。サーバーへは、画面の骨組みを取りに行くリクエストは発生せず、必要なデータ（JSON）だけをAPI経由で取得する。そのため、画面遷移がサーバーとの往復なしで一瞬で行われ、変更が必要な箇所だけが更新される。

「直接URLで404になる問題」の原因
例えばこのアプリで https://sns-timeline.example.com/posts/42 のようなURLに直接アクセス（ブラウザに直接入力、リロード、他サイトからのリンク）すると、404になることがある。

原因は、SPAではURLのパス（/posts/42）ごとの実体ファイルがサーバー上に存在しないため。通常のWebサーバーは「/posts/42 というパスに対応するファイルを探して、無ければ404を返す」という仕組みで動いている。SPAでは、/posts/42 というパスの中身（＝どの投稿を表示するか）を決めているのはブラウザ内のJavaScript（React Router）であり、サーバー側には/posts/42という実体は存在しない。したがって、サーバーが直接そのパスへのリクエストを受け取ると、対応するファイルが見つからず404を返してしまう。

「対策」
サーバー側の設定で、「存在しないパスへのリクエストは、すべてSPAの入り口となるindex.htmlを返す」というルール（フォールバック）を追加する。index.htmlが返れば、その中でReactアプリが起動し、React RouterがブラウザのURL（/posts/42）を読み取って、正しい画面（投稿詳細ページ）を描画する。
- Nginxなら try_files $uri /index.html;
- AWSでこのアプリのフロントを配信する構成（S3 + CloudFront）なら、404/403エラーレスポンスのカスタムエラーページとしてindex.htmlを200で返すよう設定する

### Q21. 楽観的UI更新

> 以下を比較してください：
> 
- サーバー応答後に更新
- 楽観的更新

そしてどちらが適切か理由付きで答えてください。

**回答:**
「サーバー応答後に更新（悲観的更新）」
ユーザーが操作した後、サーバーからの応答が返ってくるまで画面を変えずに待ち、成功が確認できてから画面を更新する方式。応答が返るまでの間はローディング表示などでユーザーを待たせる。

「楽観的更新」
ユーザーが操作した瞬間に、サーバーの応答を待たず、先に画面を更新してしまう方式。裏側では並行してAPIリクエストを送り、もし失敗した場合は画面をリクエスト前の状態に戻す（ロールバック）。

「比較」
- 体感速度：サーバー応答後は通信の待ち時間ぶん遅く感じる。楽観的更新は即座に反応し、速く感じる
- 失敗時の扱い：サーバー応答後はそもそも画面を変えていないので単純。楽観的更新はロールバックの実装が必要で複雑になる
- 失敗時の実害：サーバー応答後は小さい（何も変わっていない）。楽観的更新は一瞬でも誤った状態を見せてしまう

「どちらが適切か」
判断軸は操作の結果が重大かどうか。
- いいね・フォローなど：ほぼ確実に成功し、失敗しても実害が小さい（もう一度押せばよい程度）操作。失敗する可能性が低いからこそ、待たせるコストの方が上回る。ユーザーは頻繁に・連続してこれらの操作をするため、1回ごとに通信を待たされると体感速度が大きく損なわれる。楽観的更新で即座に反応させる方が、UXとして適切
- ログイン・決済・商品購入など：失敗する可能性が相応にあり、かつ失敗したときの影響が大きい（決済失敗なのに成功したように見せてしまうと、二重注文やユーザーの混乱を招く）操作。結果が確定するまで、誤った状態を絶対に見せてはいけないため、サーバー応答後に更新するのが適切

つまり判断基準は、「失敗する頻度」と「誤表示したときの実害」の掛け算で考える。失敗頻度が低く実害も小さいものは楽観的更新、失敗頻度や実害が無視できないものはサーバー応答後の更新、という使い分けになる。

### Q22. Docker / docker-compose

> Dockerの概要と、ローカルインストールとの違いを説明してください。
> 

**回答:**
「Dockerの概要」
Dockerは、アプリケーション本体・依存ライブラリ・実行環境の設定などを「コンテナ」と呼ばれる1つのパッケージにまとめ、どの環境でも同じように動かせるようにする技術。

コンテナには、OSそのものは含まれない。コンテナはLinuxカーネル（OSの中核部分）を間借りしながら、プロセスやファイルシステムを他から隔離して動く仕組みで、OSを丸ごとエミュレートする仮想マシンとは異なる。実行するマシンがLinuxであればそのマシン自身のカーネルを直接使い、WindowsやMacであれば、Docker Desktopが裏で自動的に用意する小さなLinux仮想マシンのカーネルを間借りする。使用者からは意識せず、Windows/Macのままコンテナを扱えるように見える。この仕組みにより、仮想マシンよりも起動が速く、リソース消費が軽い（数十MB〜数百MB程度、起動も数秒）という利点がある。

「ローカルインストールとの違い」
ローカルに直接ソフトウェア（例: PostgreSQL）をインストールする場合、動作環境がそのパソコンのOS・バージョン・既存のインストール状況に依存する。開発者Aの環境では動くが、開発者Bの環境ではOSやバージョンの違いで動かない、といった環境差異による不具合が起きやすい（いわゆる「私の環境では動く」問題）。

Dockerを使うと、必要な環境そのものをコンテナ内に固定して配布できるため、docker compose upのようなコマンド1つで、誰のパソコンでも同じバージョン・同じ設定のPostgreSQLを起動できる。OSがWindowsでもMacでも、コンテナの中身（アプリ・依存関係・設定）は完全に同一のまま配布され、かつDockerがOSごとの違いを吸収して同じコマンドで操作できるようにしているため、「同じコマンドを打てば、同じ中身が、同じように動く」が実現される。

### Q23. AWS基本サービス

> EC2 / RDS / ALB / S3 の役割と分離理由を説明してください。
> 

**回答:**
「EC2 / RDS / ALB / S3 の役割」
- EC2（Elastic Compute Cloud）：仮想サーバー。OSからアプリケーションの実行環境まで自由に構築できる、AWS上の「1台のパソコン」に相当する。このアプリではSpring Bootアプリケーションを動かす場所として使う
- RDS（Relational Database Service）：マネージド型のDBサービス。PostgreSQLやMySQLなどのDBエンジンを、AWSが構築・パッチ適用・バックアップなどを代行してくれる形で提供する。利用者はDBサーバーのOS管理などをする必要がない
- ALB（Application Load Balancer）：リクエストを複数のサーバーに振り分ける中継役。主な役割は2つある。1つは負荷分散（1台のEC2に負荷が集中しないよう複数台に分散する）、もう1つはフェイルオーバー（ヘルスチェックで異常なインスタンスを検知し、正常なインスタンスだけにリクエストを送る）
- S3（Simple Storage Service）：ファイル（オブジェクト）を保存するストレージサービス。画像・動画・静的なHTML/CSS/JSファイルなど、容量が大きくなりがちなデータの保存に向く

「分離する理由」
4つのサービスを分けている根本的な理由は、それぞれ役割・スケーリングの単位・アクセスすべき相手が異なるため。
- EC2とRDSを分ける理由：セキュリティ上、RDSを外部から直接アクセスさせず、EC2経由でしかアクセスできないようにするため（内部ネットワークに閉じ込める設計）。加えて、負荷が増えたときの対処法が異なる（EC2はインスタンスを増やす「水平スケール」で対応しやすいが、RDSはスペックを上げる「垂直スケール」が中心になりやすい）ため、独立して増減・調整できるようにする必要がある
- EC2とALBを分ける理由：ALBは「外部からの窓口」という役割に特化させ、実際の処理を行うEC2とは責務を分離する。これにより、EC2を複数台に増やしても、外部からのアクセス先（ALBのアドレス）は1つのまま変わらない
- EC2とS3を分ける理由：静的なファイル（画像等）をEC2のディスクに置いてしまうと、EC2を複数台に増やしたときに「どのサーバーにアップロードされたファイルか」が分散してしまい、扱いにくくなる。S3のような独立したストレージに集約すれば、EC2が何台に増えても、どのサーバーからでも同じファイルにアクセスできる。またS3は動的な処理（プログラムの実行）を行わないため、静的ファイルの配信に特化させることでコストも抑えられる

つまり、それぞれのサービスの「得意なこと」に特化させ、疎結合に保つことで、個々を独立して増減・保守できるようにする、というのがAWSにおける典型的な設計思想である。

### Q24. IaC（Terraform）

> 手動構築との違いとメリットを説明してください。
> 

**回答:**
「IaC（Infrastructure as Code）とは」
サーバー・ネットワーク・DBなどのインフラ構成を、手作業（管理画面のクリック操作等）ではなく、コードとして記述し、そのコードを実行することで構築する手法。Terraformはその代表的なツールの1つで、「どんな状態であるべきか」を宣言的に記述する。

「手動構築との違いとメリット」
- 再現性：同じコードを実行すれば、誰が・いつ・どの環境で実行しても、寸分違わず同じインフラが構築される。開発環境・ステージング環境（本番環境とほぼ同じ構成で用意する最終確認用の環境。実ユーザーはアクセスしない）・本番環境を同じ構成で揃えたい場合や、障害時に環境を作り直したい場合に、手動での再構築より確実かつ迅速に対応できる
- 属人化の解消：手動構築では、「設定した本人しか構成を把握していない」状態に陥りやすい。IaCではコードそのものが構成の説明書になるため、誰が見ても同じ情報を得られる
- 変更履歴の管理：コードをGitで管理することで、「いつ・誰が・なぜこの設定を変更したか」がコミット履歴として残る。手動構築では、管理画面上の変更履歴が乏しく、変更理由も残りにくい
- 変更前の差分確認：Terraformのterraform planのように、実際に変更を適用する前に「今の状態」と「コードが表す望ましい状態」を機械的に比較し、何が追加・変更・削除されるかを一覧で確認できる。手動構築では、変更を実行した後でなければ何がどう変わったかを正確に把握する手段がない。IaCでは実行前に差分を確認でき、意図しない変更（設定ミスによる想定外の削除など）に事前に気づける可能性が高まる。ただし、コードを実行するまで結果が完全に保証されるわけではない点はIaCでも変わらない
- コードレビューによる事故防止：インフラの変更をコード（プルリクエスト）として提案できるため、適用前に第三者がレビューできる。手動構築では、担当者の一存でいきなり本番環境が変更されてしまうリスクが常にある

「手動構築の問題点（まとめ）」
上記の裏返しとして、手動構築は属人化・設定漏れ・履歴の欠如に加え、「変更前に差分を確認する手段がない」「レビューを挟む仕組みがない」という点で、事故が起きたときに発見・原因追及が遅れやすい。

### Q25. 環境変数と機密情報

> ソースコードに直接書く問題点と、安全な管理方法を説明してください。
> 

**回答:**
「ソースコードに直接書く問題点」
DBのパスワードやJWT_SECRETのような機密情報をソースコードに直接書き込むと、そのコードをGit管理下に置いた時点で、Gitの履歴に半永久的に記録されてしまう。これが最大の問題。
- リポジトリがpublicであれば、誰でも閲覧できる状態になる
- privateリポジトリであっても、アクセス権を持つ全員（元従業員含む）に見えてしまう。また、後からリポジトリをpublicにする、あるいは第三者に譲渡するといった場合にも、過去の履歴ごと漏洩する
- 一度コミットしてしまうと、後から該当行を削除しても、過去のコミット履歴を遡れば値を読み取れてしまう。完全に消すには履歴の書き換え（git filter-repo等）という大掛かりな対応が必要になり、根本的な解決が難しい

つまり「後で気づいて直せばよい」では済まない、取り返しのつきにくい種類の事故である。

「安全な管理方法」
- ローカル開発では、.envファイルに機密情報を書き、.gitignoreでGit管理から除外する。これにより機密情報自体はGitの履歴に一切乗らない
- .env.example（値を空、またはダミーにしたテンプレート）だけはGit管理に含める。これにより、他の開発者は「どんな環境変数が必要か」を把握でき、.envの作り方に迷わない。このアプリでも実際にこの方式を採用している
- 本番環境では、.envファイルという形ではなく、AWSのSecrets ManagerやParameter Storeのような専用のシークレット管理サービスを使うのが一般的。これらはアクセス権限の管理、暗号化、ローテーション（定期的な値の更新）といった機能を備えており、単なるファイルより安全に運用できる。.envはあくまでローカル開発向けの簡易的な手段であり、本番運用にそのまま使うものではない

### Q26. 構造化ログ

> JSONログの利点と、MDC（requestId / userId）の役割を説明してください。
> 

**回答:**
「JSONログの利点」
プレーンテキストのログ（例: 2026-09-23 10:00:00 ERROR 予期しないエラー path=/api/v1/posts）は人間がそのまま読むには分かりやすいが、プログラムやログ収集ツール（Datadog等）が機械的に検索・集計するのには向かない。文字列の中からstatusやuserIdを正確に取り出すには、ログの書式ごとに個別の解析ロジックが必要になる。

JSONログは、{"timestamp": "...", "level": "ERROR", "status": 500, "userId": 123, "message": "..."}のように、情報がキーと値のペアとして構造化されている。これにより、ログ収集ツール側でstatus:500やuserId:123のような条件で正確に検索・絞り込み・集計ができる。障害調査で「特定ユーザーの直前のログだけを追う」「5xxエラーの発生率を集計する」といった操作が、プレーンテキストより格段にやりやすくなる。これがJSONログの最大の利点。

「MDC（Mapped Diagnostic Context）とは」
MDCは、同じリクエスト（スレッド）で出力されるログすべてに、共通の値を自動的に埋め込む仕組み。処理担当者（スレッド）ごとに1枚の掲示板のようなもので、MDC.put(...)でメモ（キーと値）を貼っておくと、以降そのスレッド上でログを出すたびに、ログ出力の仕組みが自動でその内容を読み取り、ログ行に付け加えてくれる。コード側は出力のたびにrequestIdやuserIdを指定し直す必要がない。

「requestIdの役割」
リクエストごとに発番される一意のID（DBに保存された値ではない）。最大の役割は、1つのリクエスト処理中に出た複数のログ行を、同じrequestIdで束ねて相関させられること。ユーザーからの問い合わせ対応時にも、エラーレスポンスに含まれるrequestIdを手掛かりに、対応するログをピンポイントで検索できる。

「userIdの役割」
そのリクエストを行った認証済みユーザーのID。ログをuserIdで絞り込めば、特定ユーザーに関する操作履歴だけを追跡できる。

## 🧪 第5章: テストと品質保証（5問）

### Q27. テストの種類

> 以下の違いと具体例を説明してください：
> 
- 単体テスト
- 結合テスト
- E2Eテスト

**回答:**
「単体テスト（Unit Test）」
1つのクラス・1つのメソッドを対象に、他の層（DBなど）から切り離して検証するテスト。他の層はモック（偽物）に置き換えるため、実行が非常に速く、失敗した際にどこに原因があるかを特定しやすい。

具体例：今回のアプリのFollowServiceTest（フォロー機能のService層のテスト）。DB操作を行うFollowMapperをモックに差し替え、「既にフォロー済みの相手を再度フォローしてもフォロワー数が2増えない」といった業務ロジックだけを検証する。

「結合テスト（Integration Test）」
複数の層を実際に連携させて動かし、一連の処理が正しく完了するかを検証するテスト。今回のアプリでは、Testcontainersを使って本物のPostgreSQLをDocker上に一時起動し、Controller→Service→Mapperの流れを実データで検証する（モックではなく実DBを使う点が特徴、D-54）。単体テストより実行は遅いが、「実際のSQLが正しく動くか」まで確認できる。

具体例：PostMapperTimelineTest（タイムライン取得のMapperテスト、実DBに対してSQLを発行し結果を検証）、PostControllerTest（投稿のController〜DBまでの一連の流れを検証）。

「E2Eテスト（End-to-End Test）」
実際のブラウザを操作し、ユーザーが体験する操作の流れをそのまま検証するテスト。フロントエンド・API・DBのすべてを通しで動かすため、最もユーザー体験に近い形で不具合を検出できる一方、実行が最も遅く、UIの見た目の変更にも影響を受けやすく壊れやすい。

具体例：ログイン→投稿作成→タイムラインに表示されることを確認する、といった一連の操作をブラウザ自動操作ツールで再現する。

「なぜ層によって粒度を変えるのか」
テストは「実行速度」と「実際の挙動に近いか」がトレードオフの関係にある。単体テストは速いが実際の統合状態までは保証せず、E2Eテストは実際の挙動に近いが遅く壊れやすい。そのため一般的には、単体テストを土台として多く書き、結合テストを中間程度、E2Eテストは主要な経路だけに絞って少なく書く（テストピラミッドと呼ばれる考え方）のがバランスが良いとされる。

### Q28. モック（テストダブル）

> モックの利点と注意点を説明してください。
> 

**回答:**
「モック（テストダブル）とは」
テストの対象から見て「協力者」にあたるクラス（DBアクセス、外部API呼び出しなど）を、本物の代わりに動作を固定した偽物に置き換える仕組み。

「利点」
- テスト対象を絞り込める：モック化した協力者は「呼ばれたらこの値を返す」と固定できるため、テスト対象のクラス（例：Service層）が持つロジックだけを、他の層の影響を受けずに検証できる
- 実行が速い：実際のDB接続やAPI通信を行わないため、実DBを使う結合テストより圧倒的に高速に実行できる
- 再現しにくい状況を意図的に作れる：「DB接続がタイムアウトした」「外部APIが500エラーを返した」といった、実際には意図的に再現しづらい異常系を、モックなら「この場合は例外を投げる」と簡単に設定できる。異常系のテストカバレッジを上げやすい

「注意点」
- 結合テストでモックを使うと、本来確認すべき層の挙動を検証できなくなる。例えばRepository層をモックにしてしまうと、「実際に書いたSQLが正しく動くか」は一切保証されない。結合テストの目的（複数層が連携して正しく動くことの確認）に反してしまうため、対象範囲を誤ってモック化しないよう注意が必要
- モックと実際の実装が乖離するリスクがある。モックは「本物がこう動くはずだ」という開発者の想定で作られるため、本物の実装が後から変更されても、モックは自動的には追従しない。その結果、モックを使ったテストは通り続けているのに、実際の本番コードは壊れている、という事故が起こりうる。このリスクを避けるため、モックを使う単体テストだけでなく、実DBを使う結合テスト（今回のアプリではTestcontainersを使っている）を併用し、モックの想定が実際の挙動と一致しているかを別途担保する必要がある

今回のアプリでも、FollowServiceTestのようなService層の単体テストではFollowMapperをモック化して業務ロジックだけを検証する一方、FollowMapper自体の正しさは、Testcontainersを使った別の結合テストで担保する、という役割分担がされている。

### Q29. 境界値とエッジケース

> 「1〜280文字制約」のテストケースを境界値分析で説明してください。
> 

**回答:**
「境界値分析とは」
「不具合は、値の範囲の“境目”で起きやすい」という経験則に基づき、制約の境目付近の値だけを重点的にテストする技法。「1〜280文字」のような範囲制約であれば、範囲の中央（例えば140文字）をテストしても、そこにバグが潜んでいる可能性は低い。バグが起きやすいのは、「ここまでは許可、ここからは拒否」という条件分岐が実際に切り替わる、まさにその境目であるため、そこを重点的に狙う。

「1〜280文字制約」のテストケース
境界値分析では、制約の内側の端と外側の端をそれぞれ1つずつ、合計4点をテストする。
- 0文字：エラー（成功してはいけない）。下限の外側（境界の1つ外）
- 1文字：成功。下限の内側（境界そのもの）
- 280文字：成功。上限の内側（境界そのもの）
- 281文字：エラー（成功してはいけない）。上限の外側（境界の1つ外）

### Q30. テストカバレッジ

> カバレッジの意味と限界を説明してください。
> 
> 
> 「100%＝バグなし」は正しいかも答えてください。
> 

**回答:**
「カバレッジの意味」
テストを実行したときに、プログラムのコードのうち、どれだけの割合が実際に実行されたかを示す指標。代表的なものに2種類ある。
- 行カバレッジ：全体のコード行数のうち、テストで一度でも実行された行の割合
- 分岐カバレッジ：if文などの条件分岐について、trueの場合・falseの場合の両方が、テストで実際に通過したかの割合

例えば、if (length < 1 || length > 280) { エラー } else { 成功 } というコードがある場合、「エラーになるケース」と「成功するケース」の両方をテストで実行して初めて、この分岐は100%になる。「成功するケースしかテストしていない」場合、行カバレッジは高くても、分岐カバレッジは低くなる。

「カバレッジの限界」
- 「コードが実行された」ことと「その結果が正しいか検証した」ことは別問題。カバレッジはあくまで通過した割合であり、正しさの割合ではない
- 組み合わせ爆発。条件分岐が複数絡み合う場合、すべての組み合わせパターンをテストするのは現実的に不可能なことが多く、カバレッジはあくまで「個々の行・分岐が最低1回通ったか」を見ているにすぎない

「100%＝バグなし」は正しいか
正しくない。理由は、カバレッジ100%が保証するのは「すべての行・分岐が最低1回は実行された」ことだけであり、「その実行結果が期待通りか」を検証したかどうかは別問題だから。

### Q31. フロントエンドテスト戦略

> Testing Libraryの思想と、その利点を説明してください。
> 

**回答:**
「Testing Libraryの思想」
Testing Library（React Testing Library等）の中心的な思想は、「実装の詳細ではなく、ユーザーが実際に見て・操作する内容に基づいてテストを書く」というもの。公式ドキュメントにも「テストがソフトウェアの実際の使われ方に近いほど、そのテストはより高い信頼性を与えてくれる」という指針が掲げられている。

「利点」
- リファクタリングに強い。内部のクラス名やコンポーネントの実装方法（Contextを使うかpropsを使うか、state変数の名前など）を変更しても、画面の見た目・操作方法が変わらない限り、テストは壊れない。実装の詳細に依存したテストは、リファクタリングのたびに無関係な理由でテストが壊れ、メンテナンスコストが増大する
- 本物の不具合を検出しやすい。テストがユーザー操作に近い形で書かれているため、「テストは通っているのに、実際にはユーザーが使えない」という食い違いが起きにくい

## 🧭 第6章: 設計原則と実務判断（5問）

### Q32. N+1問題

> 概念と、タイムライン例で説明してください。
> 

**回答:**
「N+1問題とは」
一覧データを取得する際、「全体を取得する1回のSQL」に加えて、各要素ごとに関連情報を取得する追加のSQLが、要素の数（N）だけ発行されてしまう問題。合計で「1＋N」回のSQLが実行されることになり、要素数が増えるほどSQL発行回数が線形に増加し、パフォーマンスが著しく悪化する。

「なぜ起きるのか」
典型的には、ループの中でDBアクセスするコードを書いてしまうことが原因。投稿一覧を1回のSQLで取得した後、各投稿に対して個別にSQLを発行してしまうと、投稿数ぶんのSQLが追加で走ってしまう。

「タイムライン例」
タイムラインに100件の投稿を表示する場合、投稿本体（本文・作成日時・投稿者情報など）は最初の1回のSQLでまとめて取得できる。しかし、各投稿に対して「自分がこの投稿にいいね済みか（isLikedByMe）」を確認しようとすると、投稿とは別のlikesテーブルを参照する必要があるため、これを投稿ごとに1件ずつ問い合わせてしまうと、投稿取得の1回＋100件分の問い合わせ100回で、合計101回のSQLが発行されてしまう。同様に、プロフィール一覧で「フォロー中かどうか（isFollowing）」を表示する場合にも同じ構造の問題が起きうる。

「対策」
投稿ごとに個別にSQLを発行するのではなく、表示対象の投稿IDをすべてまとめて1回のSQLに渡し、「この投稿ID群のうち、どれに自分がいいねしているか」を一括で取得する。これにより、投稿数が100件でも1,000件でも、SQL発行回数は常に一定（2回程度）に抑えられる。

### Q33. ページネーション

> 必要な理由と、代表的な2方式を比較してください。
> 

**回答:**
「ページネーションが必要な理由」
DBに保存されているデータが大量にある場合、それを一度に全件取得して画面に表示しようとすると、以下の問題が起きる。
- パフォーマンスが悪化する。1万件の投稿を一度にDBから取得し、JSONとして転送し、画面に描画しようとすると、通信量・処理時間がいずれも膨大になり、画面表示が極端に遅くなる
- ユーザー体験として不要。ユーザーは通常、一覧の全件を一度に見たいわけではなく、上から少しずつスクロール・ページ送りしながら見る

そのため、一覧データを一定件数ずつに区切り、必要な分だけを都度取得する仕組みが必要になる。これがページネーション。

「代表的な2方式」
①オフセット方式（ページ番号方式）
LIMITとOFFSETを使い、「何件目から何件まで取得するか」をページ番号で指定する方式。
- 利点：ページ番号でどこへでも自由に飛べる（1ページ目から5ページ目へ直接ジャンプ、など）。合計件数・総ページ数も計算しやすい
- 欠点：途中で新しいデータが挿入されると、ページ境界がずれる。例えば2ページ目を見ている間に新しい投稿が1件増えると、次にページを送ったとき、同じデータが重複して表示されたり、逆に1件飛ばされたりする

②カーソル方式
「最後に取得したデータの位置（カーソル）」を基準に、「そこから次のN件」を取得する方式。
- 利点：新しいデータが挿入されても、ページ境界がずれない。カーソル（基準となる値）を使って「そこから先」を取得するため、常に正しい続きが取得できる
- 欠点：ページ番号による自由なジャンプができない。「常に1つ前の結果の続きから」しか取得できないため、「5ページ目に直接飛ぶ」といった操作には向かない

「使い分け（今回のアプリの場合）」
- タイムライン：新しい投稿が絶えず追加される一覧のため、カーソル方式を採用。ページ境界がずれない特性が、常に新着が入り続ける一覧との相性が良い
- ユーザー検索：検索結果は追加・削除が少なく、並びも安定しているため、オフセット方式を採用。ページ番号で自由に行き来できる利便性を優先している

つまり、「一覧に新着データが頻繁に挿入されるか」が、方式選定の判断基準になる。

### Q34. 画像アップロード設計

> DB保存とS3保存の違いと利点を説明してください。
> 

**回答:**
「DB保存とS3保存の違い（画像データの場合）」
画像をアップロードする際、保存方法には大きく2つの選択肢がある。
- ①DBに直接保存する：画像のバイナリデータそのものを、DBのカラム（BYTEA型やBLOB型）に格納する
- ②S3に保存し、DBにはURLだけを持たせる：画像の実体はS3（オブジェクトストレージ）に置き、DB側はテーブルに「その画像を指し示すURL」だけを保存する。

「①DBに直接保存することの問題点」
- DBが肥大化しやすい。画像は数百KB〜数MBになることがあり、これがDBのテーブルに大量に溜まると、DBのバックアップ・レプリケーションに要する時間や容量が急激に増える
- DBのパフォーマンスに悪影響が出やすい。DBは本来、テキストや数値のような構造化データを高速に検索・更新することに最適化されており、大きなバイナリデータの読み書きは不得手
- 配信の仕組みとしても非効率。画像を表示するたびにDBへ問い合わせる必要があり、画像専用の配信最適化（CDNによるキャッシュ配信など）が使えない

「②S3に保存することの利点」
- DBの負荷から画像を切り離せる。DBはユーザー情報・投稿本文のようなテキストデータの管理に専念でき、画像の読み書きはS3が担当する。役割を分離することで、それぞれが得意な処理に集中できる
- 配信が効率的。S3は大容量ファイルの配信に特化しており、CloudFrontのようなCDNと組み合わせることで、世界中のユーザーに高速に画像を届けられる
- スケーラビリティが高い。EC2を複数台に増やしても、S3は共有の保存先として機能するため、「どのサーバーに画像がアップロードされたか」を気にする必要がない

### Q35. APIバージョニング

> 代表的な方式と特徴を説明してください。
> 

**回答:**
「APIバージョニングとは」
APIの仕様を変更する際、既存の利用者（クライアント）が壊れないようにするための仕組み。

APIの変更には2種類ある。
- 後方互換性のある変更：レスポンスに新しいフィールドを追加する、など。既存クライアントは新フィールドを無視すればよいので壊れない
- 破壊的変更（後方互換性のない変更）：既存フィールドの名前を変える、フィールドを削除する、必須パラメータを追加する、など。既存クライアントがそのまま動かなくなる

破壊的変更を行いたい場合、新旧のAPIを一定期間併存させ、クライアント側が自分のタイミングで移行できるようにする必要がある。そのために、どのバージョンのAPIを呼ぶかを指定できる仕組みが必要になる。

「代表的な3方式」
①URLパスに含める方式（例: GET /api/v1/posts、GET /api/v2/posts）
- 特徴：最も広く使われている方式。URLを見ただけでどのバージョンか一目で分かり、ブラウザやcurlでも簡単に試せる
- 利点：分かりやすく、キャッシュやルーティングの設定もしやすい
- 欠点：厳密なREST原則の観点では「同じリソース（投稿）に複数のURLが存在する」ことになり、リソースの一意性に反するという批判がある

このアプリもこの方式を採用しており、すべてのエンドポイントが /api/v1/ から始まる。

②HTTPヘッダーに含める方式（例: Accept: application/vnd.example.v2+json）
- 特徴：URLがバージョンによって変わらない。リソースのURLは常に1つであり、REST原則に忠実
- 利点：URLがきれいに保たれる
- 欠点：ブラウザのアドレスバーに打ち込むだけでは試せず、ヘッダーを指定できるツールが必要なので、動作確認やデバッグがしにくい。またキャッシュの制御も複雑になりやすい

③クエリパラメータに含める方式（例: GET /api/posts?version=2）
- 特徴：実装が最も簡単。既存のエンドポイントにパラメータを1つ追加するだけで済む
- 利点：導入コストが低く、ブラウザからも試しやすい
- 欠点：バージョンが「オプション扱い」に見えてしまい、指定を忘れた場合の挙動（デフォルトはどのバージョンか）を明確に定義する必要がある。またURLの一部として本来の絞り込み条件と混ざるため、可読性が下がりやすい

「まとめ」
実務では、分かりやすさと運用のしやすさから①のURLパス方式が最も一般的。厳密なREST設計を重視する場合に②が選ばれることがあるが、デバッグのしにくさがトレードオフになる。

### Q36. 技術選定

> 判断基準を説明し、
> 
> 
> React + Spring Boot + PostgreSQL を例に具体化してください。
> 

**回答:**
「技術選定の判断基準」
技術を選ぶ際は、「流行っているから」「新しいから」ではなく、以下のような観点を総合して判断する。
- 要件との適合性：作ろうとしているものの性質に合っているか。例えばSEOが重要なサービスならSSR、ログイン後の動的コンテンツが中心ならSPA、といった判断
- チームの習熟度・学習コスト：メンバーが扱えるか。優れた技術でも、誰も使えなければ開発速度が落ち、品質も下がる
- エコシステムと情報量：ライブラリが充実しているか、困ったときに参照できる情報（公式ドキュメント・記事・事例）が十分にあるか
- 長期的な保守性・将来性：開発が継続されているか、LTS（長期サポート）があるか、数年後も使い続けられるか
- 他の技術との相性：選んだ技術同士が問題なく組み合わせられるか（バージョンの互換性を含む）
- 実績：本番環境での採用事例が豊富か。枯れた技術は、未知の問題を踏むリスクが低い

「React（フロントエンド）」
- 要件との適合性：このアプリはタイムライン・いいね・フォローなど、画面の一部が頻繁に更新されるSNS。DOMの差分更新を効率的に行えるReactの特性が適している。またログイン後の個人向けコンテンツが中心でSEOの重要性が低いため、SSRではなくSPA構成（React + Vite）で十分
- エコシステム：利用者が非常に多く、React Router・Testing Libraryなど周辺ライブラリが充実している。このアプリでもVitest + React Testing Libraryをテスト基盤として採用できた（D-57）
- 情報量：日本語・英語ともに情報が豊富で、詰まったときに調べやすい

「Spring Boot（バックエンド）」
- 実績と安定性：Javaのエンタープライズ開発で長年の実績があり、認証（Spring Security）・DBアクセス・バリデーション・例外ハンドリングといった必要な機能が一通り揃っている。このアプリでもJWT認証・グローバル例外ハンドリング・構造化ログのすべてを標準機能の範囲で実現できている
- 長期的な保守性：JDK 25（LTS）+ Spring Boot 4.1.0という組み合わせを採用（D-28）。LTSを選ぶことで、長期のセキュリティ更新が見込める
- トレードオフの認識：一方で、最新バージョンを選んだことによるリスクも実際に発生した。Web上の情報の大半はSpring Boot 3.x向けであり、MyBatisとの組み合わせが公式メタデータ上は非対応と表示される、Jackson 3への未対応ライブラリがある、といった問題に直面している（D-25・D-26・D-28）。「最新＝常に良い」ではなく、情報量の少なさという代償を理解した上で選ぶ必要がある

「PostgreSQL（データベース）」
- 要件との適合性：ユーザー・投稿・いいね・フォローといった関係が明確な構造化データを扱い、「いいね数のカウンタ更新を同一トランザクションで行う」（D-01）といった整合性の保証が重要。トランザクションと外部キー制約を備えたRDBMSが適している
- 機能の充実：INSERT ... RETURNING idのような便利な機能を活用できている。一方でこれがPostgreSQL固有機能への依存を生み、テスト用DBとしてH2を使えない（＝Testcontainersで本物のPostgreSQLを起動する必要がある）というトレードオフも生じた（D-54）
- コスト：オープンソースでライセンス費用がかからず、AWSのRDSでもマネージドサービスとして提供されているため、本番運用への移行もしやすい

「まとめ」
技術選定は「単体で最も優れたものを選ぶ」作業ではなく、要件・チーム・保守性・相性を総合し、トレードオフを理解した上で意思決定する作業である。重要なのは、選定時に何を捨てたのかを記録しておくこと。このアプリでは、判断の経緯と代償をdocs/09_decision_log.mdに残しており、「なぜこの技術を選んだのか」を後から検証できるようにしている。
