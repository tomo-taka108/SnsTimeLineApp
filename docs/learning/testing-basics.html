テストの考え方 — 5段階の階層と、技法の使い分け

「どんなテストを、どの順で、何を使って書くのか」。テストを1本も書いたことがない状態から、実際に63本書くまでに理解したことを整理します。テスト実装の準備〜Stage 1（2026-09-01〜09-02）時点の内容です。

1そもそもテストとは何をするものか

まず結論：手で確認していることを、プログラムに代わりにやらせるだけです。

新機能を作ったとき、今まではこうしていたはずです。

1. アプリを起動する
2. ブラウザでログインする
3. 投稿に「いいね」を押す
4. 数字が 1 になったのを目で見る

テストは、この4番をコードで書くだけです。

いいねを押す  →  数字が 1 になっているはず

テストの本当の価値 中心概念

価値：今動くことの確認ではなく、3ヶ月後に壊れたら気づけること

一度書けば、コマンド1つで何百回でも自動実行できます。別の機能をいじって、うっかり「いいね」を壊しても、その場で赤くなって教えてくれます。

たとえ：健康診断。受けた瞬間に健康になるわけではないが、去年と比べて悪くなった箇所が分かる。テストも「今正しい」ことより「前と変わってしまった」ことを検出するために効く。
覚えておくこと：テストは「バグを見つける道具」というより「バグが入り込んだことに気づく仕組み」。だから一度書いて終わりではなく、以後ずっと動かし続けるものになる。

2テストの5段階（階層イメージ）

小さく速いものが下、本物に近く遅いものが上。下から順に固めていきます。

⑤ E2Eテスト
ブラウザを自動操作して、最初から最後まで通す
今回やらない
④ フロントエンドのテスト
画面のボタンを押したら期待どおり動くか（Vitest）
予定
③ 結合テスト
実DB・HTTP経由で通しで動くか（Mapper / Controller）
予定
② 単体テスト（機能）
いいね・フォローなどの判断ロジック（Service層 + Mockito）
次はここ
① 単体テスト（部品）
文字数を数える・画像か判定する、などの小さな道具
✓ 63本 完了
← 下ほど 速い・数を書ける・原因が特定しやすい

この順で進める理由はシンプルで、下の層が壊れていると、上の層のテストも意味をなさないからです。文字数の数え方が間違っていたら、画面のテストが通っても信用できません。

E2Eを今回やらない理由：ブラウザを自動操作するため遅く・壊れやすい（画面の文言を変えただけで落ちる）。学習の優先度としては、下の4層を固めるほうが得るものが大きいと判断した。

3層によって「道具」が変わる理由

判断基準はひとつ。「周りを偽物に置き換えても、確かめたいものが残るか」。

層中身は何か偽物に置き換えるとやり方
Serviceif文・順序・計算などの判断 判断は残る ○単体テスト（Mockito）
Mapperほぼ SQL だけ（XMLに記述） SQLが消える ×結合テスト（実DB）
Controllerほぼ受け渡しだけ 通す先が消える ×結合テスト（実DB＋HTTP）

なぜ Mapper を単体テストできないのか

Mapper の Java ファイルはメソッド名の宣言だけで、中身は XML に書いた SQL です。つまり自分で書いたのは SQL のほうです。ここを偽物（モック）に置き換えると、こうなります。

モック「findTimeline が呼ばれたら、この3件を返すことにします」
      ↓
テスト「3件返ってきた。OK」

  → 自分が書いたSQLは1行も実行されていない

特に怖いのが、次のような書き忘れです。

-- deleted_at IS NULL を書き忘れた（削除済みが出てしまう）
SELECT * FROM posts WHERE user_id = #{userId}

重大なバグですが、SQLを実行していないテストでは絶対に見つかりません。だから Mapper は実DBで動かすしかない、という結論になります。

MyBatis 特有の落とし穴：カラム名を書き間違えても起動時にはエラーにならず、値が黙って null になる。これも実際にSQLを流さないと気づけない。

Controller も同じ理由

Controller 自身は「受け取って渡して返す」だけですが、その周りに重要な部品が並んでいます。確かめたいのは、この一連が通しで動くかどうかです。

リクエスト
   ↓
JWT認証フィルタ        ← 未ログインなら 401
   ↓
Spring Security
   ↓
@Valid バリデーション   ← ①で作った文字数チェックはここ
   ↓
Controller
   ↓
例外ハンドラ            ← 403 / 404 を JSON に変換
まとめ：「単体テストしない層」があるのではなく、層によって呼び方と道具が変わるだけ。やらない層はひとつもない。

4ブラックボックス と ホワイトボックス

テストケースを「何を見て」作るか、という視点の違いです。

⬛ ブラックボックステスト 期待値はこちら

仕様書だけを見て作る。中身のコードは見ない。

  • 「280文字まで」と仕様にあるなら、280と281を試す
  • 実装がどう書かれていようと関係ない
  • 実装のバグに引きずられないのが最大の利点

⬜ ホワイトボックステスト 漏れの確認に

実装の中身（分岐）を見て作る。

  • if が3つあるなら、3つとも通るケースを用意する
  • 実装固有の癖（正規表現など）を拾える
  • ただし実装の誤解をそのまま正解にしてしまう危険
ホワイトボックスだけだと危ない理由：仕様が「上限100」なのに実装が「上限50」だった場合、実装を見てテストを書くと「51でエラー」と書いてしまう。実装もテストも間違っているのに、両方とも緑になる。

だから両方使います。今回の進め方はこうしました。

[1] ブラックボックス  設計書を見て、期待値の表を作る
        ↓
[2] ホワイトボックス  実装の分岐と突き合わせ、通っていない経路が無いか確認
        ↓
[3]  テストコードを書く

作った表（docs/11_test_design.md）には「根拠」列を設けて、期待値の出典（設計書のどこか）を必ず書くようにしました。ここが空欄のケースは仕様の裏付けが無い、と一目で分かります。

5ケースの作り方（3つの技法）

「なんとなく思いついたケース」ではなく、機械的に洗い出すための型。

① 同値分割 まず全体を分ける

入力を「同じ結果になるグループ」に分け、各グループから代表を1つだけ選ぶ。

文字数チェックなら「短すぎる／ちょうどいい／長すぎる」の3グループ。3文字も5文字も同じ「ちょうどいい」なので、両方試す意味はない。

ねらい：無限にある入力を、意味のある少数に減らす。

② 境界値分析 バグは境目に出る

グループの境目を狙う。min-1 / min / max / max+1 の4点が基本。

バグの多くは < と <= の書き間違いなど、境目1つ分のズレで起きる。真ん中の値をいくら試しても見つからない。

上限50文字の場合:
  49文字  … 通るはず
  50文字  … 通るはず（境界）
  51文字  … 落ちるはず（境界+1）

③ デシジョンテーブル 条件の組み合わせ

失敗のしかたが複数あるとき、表にして漏れを潰す。

実際に、カーソル（ページの「しおり」）の変換処理で表を作ったところ、当初の計画に無かったケースが4件見つかった。表にしないと頭の中では拾いきれない。

見つかった例：IDが負数のとき／前後に空白があるとき／末尾に余計な文字があるとき／null を渡したとき。
実感したこと：「境界を確認する」とメモしただけでは不十分で、どの値を叩くかまで決めて表に書くことで初めて漏れが見える。技法は難しい理論ではなく、抜けを防ぐためのチェックリストに近い。

6テスト用DB — Testcontainers と H2

「テストのせいで開発中のデータが汚れる」問題をどう解くか。

いいねのテストをするにはデータベースが必要です。でも普段使っている開発用DBをそのまま使うと、テストが作ったゴミデータが溜まっていきます。だからテスト専用のDBが要ります。ここで候補が2つ出ました。

H2 今回は不採用

すごく軽いお手軽データベース。インストール不要で、テスト開始時に一瞬で立ち上がり、終わると消える。

  • とにかく速い・準備が簡単
  • 多くのプロジェクトで使われる定番
  • 本番のPostgreSQLとは別物

Testcontainers 採用

本物のPostgreSQLを1台、自動で立ち上げて捨てる。Docker を使う。

  • 本番と同じDBで試せる
  • 終了時に自動で破棄。ゴミが残らない
  • 起動に十数秒かかる／Docker が要る

なぜ H2 が使えなかったか

料理でたとえると、このアプリは業務用オーブン（PostgreSQL）にしかない機能を使うレシピで書かれていました。H2 は電子レンジです。どちらも加熱はできますが、同じではありません。

決定的だったのがこれです。ユーザー検索のために、PostgreSQL 専用の拡張機能を有効にしています。

CREATE EXTENSION IF NOT EXISTS pg_trgm;   -- 「田中たろう」を「たろう」で探せるようにする

この命令はDBの準備段階（一番最初）で実行されます。H2 にはこの機能が無いため、こうなります。

テスト開始
   ↓
テーブルを作る
   ↓
CREATE EXTENSION pg_trgm  →  H2「そんな命令は知らない」でエラー
   ↓
停止。テストは1本も動かない
「一部が動かない」ではなく「入口で全滅」だった。他にも動かない箇所が8つあり（カーソルページング・ユーザー検索・投稿作成など主要機能のほぼ全部）、H2 用に別のSQLを書けば動かせるが、それは電子レンジ用のレシピをテストして、業務用オーブンで本番を動かすことになる。テストが通っても本番で壊れるので意味がない。

結果として、当初の心配はより良く解決された

【普段の開発】
  アプリ ──→ PostgreSQL（開発用 snstimeline）
                 ↑ 手動テストのデータが入っている

【テスト実行時】
  テスト ──→ PostgreSQL（テスト用・使い捨て）  ← 新しく起動
                 ↑ 開発用とは完全に別物
             テスト終了と同時に消滅。ゴミも残らない
学び：「H2でテスト用DBを作る」という当初の方針は考え方としては正しかった。ただし手段が今回のアプリに合わなかっただけ。目的（開発用DBを汚さない）は Testcontainers のほうがより確実に果たせた。手段が使えないとき、目的まで捨てなくてよい。

7テストが本物か確かめる（ミューテーション）

緑になっているテストが、実は何も検証していないことがある。

アサーション（確認）が緩かったり、対象を呼び忘れていたりすると、テストは常に緑になります。これが一番たちが悪い状態です。緑なのに何も守られていないからです。

そこで、わざと実装を壊して、テストが赤くなるかを確かめました。

わざと壊した内容結果
カーソルの時刻をマイクロ秒 → 秒に戻す（過去に出たバグの再現）✓ 4件が赤
WebP画像の判定を先頭4バイトだけにする✓ 3件が赤
文字数をコードポイント → UTF-16で数えるように変える✓ 3件が赤

3つとも検出できました。壊した箇所と落ちたテストがきちんと対応しており、回帰（あとから壊れること）に気づけることが実証されました。確認後、実装は元に戻しています。

合言葉：「緑だから安心」ではなく、「落ちることまで確かめて初めてテストが機能する」。

8つまずきポイント集

実際にぶつかった／回避したもの。

ポイント内容
テストは実装の写経ではない 実装を見て書くと、実装が仕様を誤解していた場合にテストも同じ誤解をする。期待値は必ず設計書から引く。
「割り切り」もテストに書く 絵文字 👨‍👩‍👧 は見た目1文字だが5文字として数える仕様。これをテストに書かないと、後から見た人がバグと誤認して直してしまう。意図的な仕様であることの記録になる。
設計書も間違う 上の 👨‍👩‍👧 を、表を作った時点では「3文字」と書いていた。実際に動かしたら5文字だった（絵文字3個＋見えない接着文字2個）。机上の想定は実行で必ず確認する。
1ケースでは検証にならないことがある 「記号が出ないこと」の確認は、たまたま出ない入力を選んでいる可能性がある。値を変えて多数試す（パラメータ化テスト）。
テストの命名規則 このプロジェクトではクラス名を *Test に統一する。*IT にすると別の仕組みの管轄になり、./mvnw test で走らなくなる。
Docker の起動を忘れる 実DBを使うテストは Testcontainers が Docker を使う。起動していないと Could not find a valid Docker environment で失敗する。
